# E40 锚点生效后重放（L2 复测）

日期：2026-11-02 15:30　执行：Lead（实验设计）+ 3 个全新上下文执行 subagent + 1 个独立评分 subagent
状态：**行为提示证据（simulated-context-behavior），非发布门禁、非用户验收**。

## 问题

L2（过度防御、复杂度失控）在上一轮文本契约下发稳定失分：E40 同 prompt 重放 3 次，criterion 2（"先查等价既有机制并说明为何不够，纯假设延后并说明代价"）稳定为 1，总分 5/6（见 `replay-E39-E42.md`）。当时的候选结论是"文本触发条件不足以保证逐条对照，结构锚点可能补强"。0.9.8-dsh.1 的插件已把四层锚点注册进 DSH 的 `systemPrompt`，且用户已于 15:2x 重启 GUI，本会话确认锚点已进入系统提示。本实验检验：**锚点生效后，E40 的 c2 是否仍稳定失分。**

## 方法

- 执行者：3 个全新上下文 subagent；只给 E40 原始 prompt 与可用技能清单（ff-intake / ff-prove / ff-review），明确禁止读取 `source/evaluations/` 与任何 criteria/rubric；不要求造任何工具调用。
- 条件差异：仅"插件四层锚点是否在 system prompt 中"。执行者与上一轮同模型、同技能文本、同工作区；上一轮的 3 次重放发生于插件锚点注册/重启之前。
- 评分：另一个全新上下文 subagent，只读 `source/evaluations/README.md` 规则、`scenarios.json` 的 E40 criteria/critical_failures 与三份响应；每 criterion 0–2，全 2 且无 critical_failures 才 PASS。
- 原始响应与评分要点已摘录进本文件（工作区临时目录 `_verify_tmp/e40-anchor-replay` 已在验证后删除）。

## 解释与边界

- 本轮唯一显著差异是 system prompt 中的四层常驻锚点；三份响应都直接引用其规则语（"已存在的等价机制、为何不够、可复现失败样本"），与锚点文本高度对应。合理推断：**常驻、每次请求都可见的锚点比按需读取的技能文本更能覆盖 L2 这条检查。**
- 样本量很小：两种条件各 n=3，3/3 → 0/3 的 Fisher 精确检验双尾 p≈0.10，**不足以保证统计显著**；这是"可复现行为提示"，不是稳定复现声明。
- 同模型、同技能文本、同一天；评分者的 2 分依据是"规则被正确引用并落到决策"，并非证明执行者真的逐条枚举了项目内既有机制（执行者未读仓库）。因此 c2 的改善首先是"检查意识被激活"，其次才是"逐条对照"。
- 不代表原生宿主集成、真实用户验收或生产行为；仍受 `source/evaluations/README.md` 的结论边界约束。

## 结论

在锚点生效后的同协议重放中，E40 由 3/3 次 5/6（c2 稳定失分）变为 3/3 次 6/6 PASS。L2 从"稳定失分"降级为"锚点覆盖下可复现通过，但样本小、证据强度有限"。本迭代不因此再加任何新机制；后续若要提高 L2 证据强度，应扩大样本或换模型复测，而不是继续增加常驻文本。

## 附录：三份响应原文

## R1
【判断】不实施 —— 该方案应退回，先补失败样本与根因，再谈修复。

任务原话：只修"设置页保存偶尔失败"。AI 提议捆绑引入：(1) 统一状态库 (2) 自动路由层 (3) 新测试框架，理由"以后扩展需要"。

一、L1 整体偏航（无当版验收证据）
- 三项提议没有一项对"保存偶尔失败是否被修好"负责，无法用真实入口验证；总需求被换成"平台建设"。
- "偶尔失败"本身尚无可复现失败样本：触发频率、场景、错误码/日志、复现步骤都缺。没有稳定失败信号，任何修复都无法证明有效，架构改动更无法验收。

二、L2 过度防御（复杂度失控）
- 理由"以后扩展需要"是纯推测，不是失败样本。按契约：新增机制前必须先指出"已存在的等价机制、为何不够、可复现失败样本"；这里三样都没有。
- 自动路由层与"保存失败"甚至没有可陈述的因果链；这是最明显的无依据项。
- 成本：新增三个常驻设施 = 长期维护、迁移风险、团队认知负担，对一次 bug 修复严重不成比例；且回归面被放大到设置页之外。

三、L3 过早接受大方案（未比较更简单替代）
更简单的替代（应作为首选）：
 A. 先复现与定位：埋点/日志记录失败请求、错误码、时序、并发写、存储配额/权限、乐观更新回滚、表单校验时序；定位根因。
 B. 最小修复：按根因加最小重试/去抖/幂等/串行化，改动面限制在设置页保存链路。
 C. 回归保护：用项目现有测试机制补一条走真实入口的回归用例（一次失败→重试成功），而不是"新测试框架"。
 A+B+C 的收益/风险明显优于捆绑三项重构；若仍要选 B 方案（重构），必须给出可证伪实验证明"仅最小修复无法解决"。

四、L4 问题被替换
- 用户说的是"保存偶尔失败"，方案把问题重定义为"架构不够先进"。设计讨论 ≠ 实现授权；bug 修复票不构成引入状态库/路由层/测试框架的授权。
- 捆绑交付的副作用：验收口径模糊（bug 是否修好被架构改动掩盖）、周期拉长、回滚困难、评审焦点分散。

五、可辩护的边界（不是全盘否定）
1) 为复现"偶尔失败"而加的临时观测/日志 —— 合理，属于定位手段，但应最小化并可移除。
2) 若根因确实落在状态同步（如设置页与其他视图状态不一致导致覆盖写）—— 那时"统一状态库"才进入候选，且需：失败样本 + 现有机制为何不够 + 成本/收益 + 用户确认，独立成提案走 intake/spec/plan。
3) 若项目当前完全无测试手段，最小测试能力可作为独立小决策提出，但不应以"新框架"形式捆绑进本次修复。
4) "自动路由层"在无路由相关证据前不应立项。

六、建议下一步
1) 定义"偶尔"：频率、环境、错误信息、可复现步骤；拿到至少一条可重复失败信号。
2) 用现有机制加最小埋点定位根因（只读、可回滚）。
3) 提出单一最小修复 + 一条真实入口回归用例，附验收口径（什么现象算修好）。
4) 把三项架构提议拆出，标注"无失败样本、未获授权"，等用户明确要求扩展时再评估。

结论：方案不应实施；先补证据、缩范围、按根因最小修复。

## R2
【判断】不应实施。该方案把"修一个偶发缺陷"替换成"平台化改造"，与原始目标没有因果链，也没有失败样本支撑，属于过度防御 + 范围偷换。

【理由】
1) 原始问题被替换：用户原话只是"设置页保存偶尔失败"——一个待定位的缺陷。提议把它重命名为"状态管理/路由/测试设施不足"，但没有任何证据把三者与"偶尔失败"连起来。
2) 缺根因证据：偶发保存失败的常见根因是并发/竞态、超时与重试、错误被吞、序列化或脏数据、保存顺序被覆盖等。这些都不会因为引入统一状态库、自动路由层或新测试框架而自动消失。根因未定位前，改了也无法判断是否修好，更无法证伪。
3) "以后扩展需要"不是验收标准：这是不可证伪的未来假设，不能充当本版通过的证据。L2 要求：为"以后可能"新增机制前，先指出已存在的等价机制、说明为何不够，并给出可复现失败样本。三项提议均无。
4) 三项各自也缺必要性：统一状态库——保存是否真的败在跨组件状态不一致？若不是则无关；自动路由层——与"保存失败"无直接关系；新测试框架——若已有测试设施，替换框架是基建重构并带迁移风险，最小正确动作是把复现固化成一条回归用例，而不是换框架。
5) 反效果风险：大范围改造会改变保存的触发时机与顺序，可能掩盖或制造新的偶发失败，让本就难复现的问题更难归因，同时把用户等待周期拉长到一个尚未证明有效的方案上。

【建议（最小可验证）】
- 先有界诊断：收集失败样本（时间、操作路径、接口返回/网络、错误日志），尝试稳定复现，明确"偶尔"的触发条件；
- 定位根因后做最小修复，改动面越小越好；
- 用该真实失败样本做回归证据；已有测试设施内加一条用例即可，不新建框架；
- 本版验收口径应是"在该失败样本上通过 + 观测窗口内无复发"，而不是"引入了状态库/路由层/测试框架"。

【何时才考虑这些改造】诊断证明根因确实来自状态不一致或路由缺失、且被复现的失败样本直接指向它们；同时用户明确把架构改进作为独立任务授权（单独 spec/plan、单独验收），不夹带在缺陷修复里。

（本次为纯判断，未读取仓库文件；未改动任何代码。）

## R3
结论：不应按现方案实施。应驳回这次范围扩张，先把"设置页保存偶尔失败"复现并定位根因，再做最小修复；三项基础设施改造即使将来要做，也必须另有证据、单独授权、单独验收。

理由：
1) 原始问题没有被证明需要这些改造。修复"偶尔保存失败"需要的是可复现的失败信号与根因（失败率、触发条件、保存请求是否发出/响应、控制台与存储报错、时序），而不是状态库、路由层、测试框架。当前没有任何失败样本证明现有机制不够用，这属于无证据的预防性建设。
2) "以后扩展需要"不可证伪，且把"修一个页面的失败路径"替换成了"全局架构愿景"，验收口径随之模糊——修没修好、以什么为准都说不清。
3) 三项都是横切变更，风险叠加且恰好落在故障区：统一状态库改变数据流与持久化时序，自动路由层改变页面生命周期与导航，这两者本身就可能造成"保存偶尔失败"（竞态、卸载时写入、状态被覆盖）；在根因未知时引入，会掩盖 bug 或制造新 bug，回滚粒度也变粗。新测试框架是工具链迁移，与 bug 修复无因果关系，却拖长交付、污染 diff。
4) 顺序反了：正确顺序是 复现 → 根因 → 最小修复 → 回归证据 → 若证据显示结构性问题再单独提案重构。测试方面只需为该失败路径补一个能真实复现的回归检查，不需要"新测试框架"。
5) 授权边界：用户只授权修 bug。统一状态库/路由层/测试框架是新增范围，需用户明确同意，不能以"以后需要"自行扩权。

部分成立的例外（仍需证据）：
- 若复现证明失败源于设置页数据流的状态不同步/写入时序（如基于过期快照保存），状态收敛可作为修复手段之一，但应是最小改动、限定在设置页，而非"统一状态库"。
- 若现有测试设施确实写不出该回归用例（有具体证据：无入口、无法 mock 网络/存储），才可单独提"补测试能力"，范围限于所需能力。
- 自动路由层基本没有成立理由，除非根因被证明是路由/页面生命周期导致且最小修复不可行。

候选对比（更简单的替代）：A 复现+最小修复（推荐，改动局部、可回滚、验收明确）；B 现提案（三项横切改造，风险与范围不可控）；C 折中（先 A，修复后再按证据单独立项所需的那一项能力）。
建议下一步：收集失败证据并建立可重复失败信号 → 定位根因 → 只改设置页保存路径的最小修复 → 用现有框架补回归测试 → 验收后再评估是否需要结构性改造。
