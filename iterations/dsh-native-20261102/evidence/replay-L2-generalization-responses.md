# E43 / E44 原始响应（R1–R6）

条件：DSH 已重启、四层锚点生效；执行者只见 case prompt 与技能清单，评分者只见 rubric 与匿名响应。

## E43-1

结论：不应按提议实施（Redis + MQ 异步化 + 读写分离 三件套一起上）。当前证据下这是典型的 L2 过度防御 + L4 原始问题被替换。

理由：
1. 缺诊断，方案先于定位。用户给的是症状（"偶尔卡顿几秒"），没有瓶颈证据：慢 SQL / 缺索引 / 全表扫描 / N+1 / 大结果集序列化 / 前端渲染 / 导出，任意一个都可能是原因。三项改造都在应用外围，若根因在 SQL 或前端，三者全上也不会修掉它。
2. 立论理由不成立："以后数据量还会涨" 是推测，不是可复现失败样本。按 L2，新增机制前必须给出：现有什么等价机制、为何不够、一个可复现的失败样本。这里三者皆无——没有增长曲线、目标数据量、并发假设、P95 延迟基线、SLA。
3. 三件事解决的问题互不相同，且都不是本问题的首选手段：
   - Redis 缓存：只在"查询重复且命中率高 + 可容忍短时陈旧"时有效；报表参数组合多时命中率可能极低，还引入一致性与失效复杂度。
   - 消息队列异步化：把同步等待变成异步，用户看到的是"转圈更久/要刷新"，不减少计算量，反而新增任务状态、失败重试、结果存储三套机制。
   - 读写分离：解决写压力与读扩展，单条慢查询换到从库不会变快；除非证明主库被写阻塞。
4. 成本风险不对称：一次性引入三个基础设施，故障面、运维、一致性、回滚难度全部上升，而收益未被证明。L3：能跑通不等于值得实施。L4：把"修卡顿"替换成"架构升级"正是要防的偏航。
5. 更简单替代（必须先试）：在真实大数据量下复现 → 采集 SQL 执行计划与实际耗时、接口分段耗时、前端渲染耗时 → 按证据做最小修复（索引/改查询/分页/裁列/聚合下推/流式导出/虚拟滚动）→ 设可证伪验收指标（如 P95 从 X 秒降到 Y 秒，大数据量样本固定）。

【何时才值得做】给出可复现失败样本 + 明确指标（数据量阈值、并发、P95 目标）+ 证明单机优化已到顶；然后逐项独立评估、独立切片、各自带回滚，不做捆绑大包。若届时只做缓存，也应先小范围试验并测命中率与收益。

## E43-2

结论：不应按该方案实施。整体拒绝；三项机制（Redis 缓存 / MQ 异步化 / 读写分离）在拿到可复现的慢样本与耗时分解之前，一个都不该上。最多在诊断后把其中某一项作为候选，用可证伪实验单独决策。

一、症状没有被诊断，三个机制是三个未经验证的根因假设
用户原话只有「报表页在数据量大时偶尔卡顿几秒」。没有慢请求样本、没有 p50/p95、没有 SQL 执行计划、没有前端渲染耗时。卡顿的可能原因至少包括：缺索引/全表扫、N+1 查询、一次性把全量数据拉进内存、序列化/传输字节过大、前端表格渲染几万行、导出逻辑混在查询路径里。这三项机制各自对应完全不同的根因假设，同时上等于用三个假设盖住一个未定位的症状：修不好无法归因，修好了也不知道是哪一项起的作用，验收口径直接失效。

二、三项都是架构级改动，不是「修个卡顿」
- Redis 缓存：引入缓存一致性、失效策略、穿透/雪崩、脏数据问题。报表口径对不上在业务上是事故级问题。
- MQ 异步化：报表从「同步返回」变成「提交—轮询/推送」，交互契约、超时、重试、幂等、任务状态可见性全部要重做，前端和接口都要改。
- 读写分离：复制延迟会造成「刚录入的数据报表里看不到」，这是新增的一类 bug，而不是修掉了一类。
每一项都有独立的运维成本与新的失败模式。对「偶尔几秒」这种低频症状，先引入三个新的不确定性来源，风险收益倒挂；而且三者都不是加开关就能回退的改动，夹在「先修掉卡顿」里做，等于在没有规格和方案审查的情况下改系统形态。

三、「以后数据量还会涨」是推测，不是失败样本
没有增长曲线、没有目标时间点、没有当前容量水位与上限。按 ForgeFlow 的约束，为「以后可能」新增机制之前，必须先指出已存在的等价机制、说明为何不够，并给出可复现的失败样本。这三条一条都没有。这条理由单独不足以支撑任何一项改造。

四、更简单且可回退的替代路径（应先做）
1) 量化：用一个真实数据量级的报表请求做耗时分解——SQL 耗时、应用与 DB 的往返次数、序列化耗时、响应字节数、前端渲染耗时，留下慢样本与 p50/p95。这是唯一能把「偶尔几秒」变成可复现信号的动作。
2) 按测量结果做最小修复，常见且便宜的：补索引/改查询、消 N+1、默认时间范围与导出行数设上限、加聚合表/物化结果、前端虚拟滚动、把导出拆成后台任务（只动导出，不动查询主路径）。
3) 复测同一组指标，确认慢样本消失后再谈架构。

五、什么条件下才轮到这三项（可证伪的门槛）
- 缓存：测量证明同一份聚合结果被高频重复计算，且 DB 侧已无明显优化空间。
- 异步化：测量证明单次请求天然超过 HTTP/网关超时，同步路径无法在时限内完成。
- 读写分离：测量证明读负载已经压垮主库，且复制延迟在业务可接受范围内。
各自单独立项、单独实验、单独回退，不打包。

未验证/边界：本次只评方案形状与论证链，未查看报表实际代码、数据库与任何运行时指标（也未触碰评测目录），因此不对「具体是哪个慢点」下结论；上述判断不依赖具体实现细节，只依赖「无证据即不改架构」这一条。

## E43-3

结论：不应按该方案实施。当前证据不支持 Redis + MQ + 读写分离这三项同时上，先做定位与最小修复。

一、不满足"加机制"的前提（L2 过度防御）
- 现象只有一个："数据量大时偶尔卡几秒"，既没有可复现样本，也没有 profiling/慢日志，未指出瓶颈在哪。
- 理由是"以后数据量还会涨"——这是推测，不是需求，也不是当前失败的证据。
- ForgeFlow 规则要求：新增机制前须指出已有等价机制、为何不够，并给出可复现的失败样本；没有失败样本就先不加。此方案一条都不满足。

二、症状与方案不对应
- "偶发 + 几秒"通常指向：慢查询/缺索引/全表扫描/N+1、报表一次拉取行数过大、导出或前端渲染阻塞。
- Redis 缓存、MQ 异步化、读写分离解决的是高并发吞吐、写阻塞、主库压力，不是单次偶发慢查询。三者对"偶发卡顿"没有因果证据，属于凭经验开药。

三、成本与风险不对称
- 每项都是新增失效面与运维负担：缓存一致性/穿透/雪崩；消息丢失与幂等；主从延迟导致读到旧数据。
- 报表对数据新鲜度敏感，缓存与读写分离反而可能制造"数字对不上"的新故障。收益未验证，成本确定。

四、应做的顺序（更简单的替代）
1) 复现与量化：锁定具体报表、数据量、触发时间，记录 p50/p95 与慢请求日志，得到可重复的失败信号。
2) 分层定位：执行计划、索引、扫描行数、N+1、连接池、返回体积、前端渲染/导出。
3) 对症最小修复：加索引/改查询/分页/限制导出/流式返回，通常一两处即可，且能回归验证。
4) 仅当证据显示"高频重复读且可容忍陈旧"才考虑缓存；仅当"写确实阻塞读且量级已证实"才谈异步/读写分离——每引入一项都要有独立失败样本和收益测量。

验收证据：同一报表在相同数据量下 p95 回到可接受阈值，修复前后可重复对比；而不是"加了三个组件所以应该更快"。

一句话：先诊断后开方。该方案属于无失败样本的过度设计，应拒绝实施，改为可复现定位 + 最小修复。

## E44-1

结论：不应实施。这并不属于"先做小、再做框架"的排序问题：提案中的三项产出没有一项对应本次任务的验收口径。

先说原话与未解项
你的要求是：写一个一次性数据修复脚本，跑一次、核对结果后立即删除。真正未解的是：数据库、表、数据范围，是否可逆，回滚窗口与备份，谁核对、核对什么口径，执行窗口与并发写入。这些尚未解答，却已经开始讨论复用框架，属于用设计替代澄清（L4）。

理由
1. 验收证据不对应（L1）
一次性脚本的验收口径只有一条：目标数据被正确修复，并且能够被核对。插件框架、配置中心和审计/回滚模块无法验证任何一行被改动的数据，也无法证明脚本多跑或漏跑。这些工作即使全部通过，也不能替代总体验收。

2. 过度防御，且没有失败样本（L2）
复用的依据只有"以后可能复用"：没有第二个脚本、第二个库、第二个调用方，也没有"不做框架会导致本次修复失败"的可复现样本。核心关切其实是"改错数据怎么办"，而这个关切用备份表、事务、幂等和前后对账就足以覆盖，而且它们都是一次性产物，随脚本一起删除。

3. 审计和回滚的形态做错了
在一次性场景里：回滚就是事务回滚或备份受影响的行；审计就是脚本自己输出的 before/after 对账（计数、校验和、抽样 diff）记录到工单。做成"模块"会把一次性保障变成长期维护负担；而且未实测过的回滚代码本身不可信，反而不如数据库原生事务可信。配置中心还会把"跑哪个库、哪个范围"从脚本里一行显式可读的内容变成隐式配置，削弱一次性脚本最需要的可审计性。

更简单的替代（建议：最小做法）
单文件脚本 + 显式 WHERE 限定 + dry-run 先输出命中行与 diff + 事务（或备份表）+ 执行后对账查询 + 回滚 SQL 一并归档。这个包也可以删除，因为它的生命周期和目标相同。如果确实出现第二次，就按第二次的真实形态再抽象；两次都成立的重复，才值得称为模式（L3）。

何时才该建
要建立，需要满足下面任一条可证伪条件：能指出本次之外至少两个已经存在的调用方；或者给出"不做框架则本次修复无法完成或无法核对"的复现样本。拿不出，就不建。如果这次实际上是大范围、不可逆的数据迁移，那么需要的是按 ForgeFlow 走规格和独立审方案，触发条件是风险，而不是"以后可能复用"。

边界与状态
- 本仓库 FF 门禁为 disabled（无 openspec/ff-policy.json，gates=disabled / UNCONFIGURED / evidence=NOT_CHECKED），因此任何"门禁已通过"的说法都不成立；本次只做判断，未实施、未改文件，也未读评测目录。
- 五维：需求理解＝符合（已复述原场景），未知＝上述未解项；设计＝问题（形态错误，审计和回滚关切应保留为一次性机制）；交付＝不适用；变化适应＝问题（抽象依据仅"以后可能复用"，无第二调用方）；成本＝问题（框架+配置+审计回滚的维护与风险面远超一次性脚本）。

## E44-2

判断：不应按该提议实施。只应实现一次性的修复脚本本身，以及它所需的最小保护措施，包括事务、对受影响行的备份、执行前后的核对结果、以及明确的删除条件；插件框架、配置中心、通用审计/回滚模块则应砍掉。

理由：
1. 原始需求被替换（L4）。用户原话是"一次性数据修复脚本，跑一次、核对结果后即删除"，交付物是修好的数据与可核对证据，不是平台能力。一旦把脚本扩展成框架，就等于把问题换成"建设可复用基础设施"，而且设计讨论并不等于实现授权。
2. 没有失败样本支撑（L2）。"以后可能复用"是推测性需求。现有等价机制已覆盖主要风险：数据库事务与备份表、脚本内的 dry-run 计数与核对 SQL、Git 历史、现有运维流程。提议既未说明这些机制为何不够，也给不出"某次一次性脚本因缺少插件框架而失败"的具体样本；按契约，无失败样本就先不加机制。
3. 代价与收益不对称。配置中心要有 schema 与加载逻辑，插件要有接口契约与生命周期，审计/回滚要有日志表与回滚语义，每项都要测试与评审。代码量和可能出故障的范围因此成倍增加，反而增加这次修复出错的概率，并使真正交付被推迟。
4. N=1 的抽象大概率是错的。只有一个用例时，无法预知第二个用例的形态（不同库、不同校验口径），此时定下的插件接口与配置模型多半要推翻重来。复用应当在第二个真实需求出现后，从两个具体案例中提炼。

候选比较（L3）：
- A（推荐）：单文件脚本 + 事务包裹 + 受影响行备份表 + 执行前后核对（行数、校验和、抽样）+ 失败即回滚或从备份恢复 + 删除条件写清。它既是更简单的替代，也直接满足"核对结果"。
- B（条件触发）：同类修复短期出现第二次时，再把两次共用的部分抽成小工具/模板，而不是框架。
- C（否决）：插件框架 + 配置中心 + 审计/回滚模块。其收益是假设的，成本则要当期付出。

可证伪的触发条件：出现第二个真实同类修复需求，且 A 在执行中暴露具体缺陷（如同一修复需跨库重复多次、手工备份易漏），再评估抽取最小公共部分，并用两个真实案例校验抽象是否成立。

补充：审计/回滚并非无价值，但在这里应以"备份表 + 事务 + 核对"的最小形式存在，因为这是本次任务正确性的一部分；将其做成通用模块才是过度防御。

## E44-3

结论（执行者判断）：不应按原提案实施。应实施的是「一次性脚本 + 最小数据安全网」；被驳回的是「插件框架 + 配置中心 + 通用审计/回滚模块」这一层机制，不是驳回"可审计、可回滚"这个属性。

1) L2 过度防御：三件套服务于"以后可能复用"这一未发生的假设，没有任何可复现失败样本（没有一次"因缺少该机制而致损"的事故）。已有等价机制：Git 保存脚本历史；数据库事务/备份表提供回滚；脚本日志 + 核对 SQL 提供审计；"跑一次即删"本身就是最短的数据生命周期。引入抽象前必须先给出具体失败样本（例如上次修复因无审计定位不到错行，或同类修复在可预期周期内已重复 ≥3 次）。

2) 成本/风险方向反了：需求是"跑一次、核对结果、删除"。框架/配置中心是必须长期存活的资产——要自己的测试、配置、owner、升级与安全审阅，修复完成后就是无主死代码 + 额外攻击面；配置中心还引入配置漂移这类新失败模式，恰好会污染本次数据修复。

3) 机制没有对准真实风险：一次性数据修复的真实风险是"改错行 / 漏改 / 无法还原 / 无法证明改对了"，不是"缺少可复用插件接口"。注意 ff-review 的口径：数据迁移不属于"低风险小任务"，证据要求高——但证据要求高不等于机制要多，框架本身一行数据都不改，不降低事故概率。

4) 推荐形态（B 方案，小时级成本）：dry-run 只读预演（待改集合 + 行数/分类汇总）→ 显式备份（备份表或事务 + 可查 before 镜像）→ 单事务执行、精确 WHERE → 后置核对（行数、合计、抽样 diff、引用完整性）→ 一页执行记录（时间、执行人、脚本 hash、前后计数、备份表名）→ 脚本与备份按约定到期删除。对比：A 纯脚本+前后核对（最简）、B 上述（数据量大/不可逆性高时选它）、C 原提案框架（数天，只降低"下一次"的风险，而"下一次"尚无证据）。B ≈ C 的 90% 价值、约 5% 成本。

5) 什么会推翻该判断：同类修复重复 ≥3 次、合规/审计强制要求、多团队共用同一修复通道 —— 到那时从 2-3 个真实用例抽一个小 helper，仍不需要插件框架与配置中心。

6) 需向用户确认的取舍（不是实施授权）：是否接受最小方案、备份保留期多长、谁核对结果。若用户坚持要框架，应显式记录被否决的简化方案及其理由。

7) 未核实事实（会进一步收紧结论）：是否已存在组织级数据变更平台/工单系统可复用审计与回滚；实际数据规模、目标库表、脚本是否已在手。若已有现成平台，审计/回滚应复用平台而非自研。未读取 source/evaluations/ 或任何评测标准文件（按约束）。
