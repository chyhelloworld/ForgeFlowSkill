# L2 双向校准重放：E45 / E46（锚点生效后）

## 为什么补这两个场景

此前 L2 的证据都只覆盖一个方向：**没有失败样本时，执行者会不会加不该加的机制**。E40（锚点前 3/3 次 5/6 FAIL，锚点后 3/3 次 6/6 PASS）、E43、E44 都在测“拒绝过度防御”。这留下一个反向风险：常驻锚点可能把执行者推向**一概拒绝必要机制**，把 L2 的防护变成另一种失效（该修的 bug 不敢修、有证据的机制不敢采纳）。

因此新增两个双向校准场景（写入 `evaluations/scenarios.json`，44 → 46）：
- **E45 有失败样本支撑的幂等修复应采纳**：支付回调重复发货 3 次、日志显示两次并发、去重是单实例内存、服务 2 实例；提议为数据库唯一约束 + 幂等记录表 + 回放测试。c1 要求确认失败样本/根因后**实施必要修复**，而不是以“避免过度设计”惯性否决；c2 要求说明内存去重的边界并比较最小方案成本；c3 要求当版验收/回滚且不捆绑事件总线/支付重写。
- **E46 混合方案：采纳有证据部分，延后无证据部分**：导出 OOM 复现 3 次（200 万行全量载入）；提议分批流式 + 顺带通用任务编排平台与配置中心（“以后导出任务会变多”）。c1 要求采纳有样本支撑的最小修复并以 OOM 样本验收；c2 要求无证据的平台/配置中心延后并说明现有机制与代价；c3 要求平台化不得成为前置，给出拆分顺序与再入场条件。

## 方法

1. 场景写入 `evaluations/scenarios.json`，schema 与既有场景一致（prompt + 3 criteria + critical_failures）。
2. 每个场景用 3 个全新上下文执行者（subagent），只给 case prompt 与可用技能清单（`ff-intake` / `ff-prove` / `ff-review`），明确禁止读取 `source/evaluations/` 或任何 criteria/rubric；执行者不知道本轮在验证 L2 校准，也不知道评分规则。
3. 六份回答由 Lead 复制为匿名文件 R1–R6（R1–R3 对应 E45，R4–R6 对应 E46），再交一个全新上下文的独立评分者：只读 `source/evaluations/README.md` 的评分协议、`scenarios.json` 的 E45/E46 criteria 与 critical_failures、以及 R1–R6 原文；评分者未参与生成，评分前未读取期望标签。
4. 评分口径：每案 3 criteria 各 0–2；三项全 2 且无 critical_failures 才 PASS。完整盲评报告见 `replay-L2-calibration-scoring.md`；六份原文见 `replay-L2-calibration-responses.md`。

### E45：有证据的必要修复被采纳，同时范围被收窄

三份回答都没有掉进“拒绝加机制”的反射：
- 都确认根因是“跨实例共享去重状态缺失 + check-then-act 竞态”，并据此采纳**数据库唯一约束**作为权威去重点；R1/R3 明确把去重与发货写入放在同一事务内。
- 都对“幂等记录表”做了成本判断：R1 “只有需要按支付方 event_id 去重，或需要保存原始响应体时才建立”；R3 “真正必要的是一个唯一键，独立幂等表只是载体”；R2 给出“若现有发货表已有业务唯一行，优先在它上面加约束或条件更新，比新建通用幂等表更小”。这是收窄范围，不是否决修复。
- 都延后了无证据的机制：Redis/分布式锁、MQ、outbox、通用幂等框架；R2 还指出“不要先查再插”的并发穿透边界。
- 验收都要求能复现原故障的并发测试（两实例/两连接），而不是顺序回放：R2 “修复前红（两次发货），修复后绿（一次发货）”；R3 要求 red 证据必须在修复前取得。

### E46：有证据的部分采纳，无证据的平台化延后

- 三份都只实施“读写两端有界内存的分批/流式导出”，并把“有界”具体化为服务端游标/keyset、固定批大小、边读边写、背压与异常清理；R5 还指出写文件端（XLSX 工作簿模型）本身可能全量驻留，必须实测而不是只改 fetch size。
- 三份都把通用任务编排平台/配置中心判为“借故障扩张范围”：没有第二个任务类型、没有调度/重试/配额/多环境配置的失败样本；“以后导出任务会变多”是预测，不是当版验收证据。
- 都给了拆分顺序与再入场条件（第二个真实任务类型、请求超时/重启续跑样本、配置多环境漂移样本），平台化没有被设为前置。
- 验收都用已复现的 OOM 场景（原入口、200 万行）并给出可证伪口径：R5 “对比 20 万行与 200 万行的峰值内存应接近、不随行数线性增长”。

## 与已有证据的关系

| 条件 | 场景 | 结果 | 说明 |
| --- | --- | --- | --- |
| 锚点前 | E40 | 3/3 次 5/6 FAIL（c2=1） | 只测“拒绝无证据机制” |
| 锚点后 | E40 | 3/3 次 6/6 PASS | 同上 |
| 锚点后 | E43 / E44 | 各 3/3 次 6/6 PASS | 同上，两个不同领域 |
| 锚点后 | **E45 / E46** | **各 3/3 次 6/6 PASS** | **反向校准：该采纳的有证据机制仍被采纳** |

六份回答末尾都带出了同一行常驻锚点（“ForgeFlow 四层失效自检（常驻；完整规则见 ForgeFlow 的 INTENT-LOOP 契约）”），说明锚点已进入执行者的 system prompt；这是“锚点在场”的操作性证据，不是行为因果的单独证明。

## 边界

- 每案 n=3、同模型同日、合成场景；这是 `simulated-context-behavior` 类证据，不是真实项目验收，也不能声称 L2 已“解决”。
- 双向校准只说明“在这两个 prompt 上，执行者既拒绝了无证据机制、也采纳了有证据机制”；不能外推到所有 L2 判断。
- 本轮**没有**因为结果好看而新增任何常驻文本、技能规则或机制；E45/E46 只是评测场景与证据。若后续出现稳定失分，再加最小、证据驱动的改动。
- 软点（评分者记录、未扣分）：E46 三份对 c2 的“现有机制为何够用”主要以“无失败样本/应先查等价机制”反证，未正面描述现有 cron/脚本覆盖当前单一导出任务；R1 回滚段“删约束/表”与“幂等记录保留”措辞有歧义，且未提示回滚会重新暴露重复发货。
