说明：执行者只收到 case prompt 与技能清单（ff-intake / ff-prove / ff-review），明确禁止读取 source/evaluations/ 或任何评测标准；评分者只读到 R1–R6 编号，评分后才由 Lead 还原对应关系。

## R1（原 E45-1）

判断：部分实施（方案方向正确，但范围需要收窄，部分机制应以更简单的方式实现或延后引入）

应实施
- 用数据库唯一约束作为跨实例的权威去重，替换或补充当前的单实例内存去重。
- 把发货状态变更与去重判定放在同一个数据库事务中完成；重复命中时返回首次成功的结果，而不是返回错误。
- 保留回归测试，但要从“一次回放”升级为“并发投递 + 顺序重放”两类。

应延后或不做
- 独立的“幂等记录表”是否必要取决于唯一键的选择：如果以 `order_id` 为键，且发货结果可以从发货/订单表读回，那么就不必新增第二张状态表，因为两表并存容易出现状态不一致；只有需要按支付方 `event_id` 去重，或需要保存原始响应体时才建立。
- 通用幂等框架、Redis 分布式锁、MQ exactly-once、全链路 outbox：当前只有一条链路出过问题，缺少可复现的失败样本，因此先不引入。
- 历史 3 笔重复发货的冲正与追责：单独立项，不随本次修复一起实施。

理由
1. 根因证据充分：服务有 2 个实例，而进程内 map 无法跨实例共享去重状态；日志显示两次回调并发到达，形成 check-then-act 竞态，即使只有一个实例也可能重复发货。两者都指向“需要一个所有实例共享、持久、可原子仲裁的裁决点”，而数据库唯一约束是现有技术栈里成本最低、且崩溃后仍有效的选择，优于内存去重和带 TTL 的分布式锁。
2. 题目没有提供以下关键信息（它们是实施前必须核实的输入，不应靠猜）：回调是否携带稳定的 `event_id`；如果支付方重试时更换 `event_id`，按 `event_id` 去重会漏掉重复，因此应以业务键 `order_id/payment_id` 为准。发货是本地事务写库，还是调用外部 WMS/物流；如果是外部副作用，唯一约束只保证“至多进入一次发货流程”，不能保证外部副作用恰好一次，提交前崩溃仍需 outbox/对账兜底，这属于第二步。订单与发货是否 1:1、现有表结构如何，这决定唯一键放在哪张表、是否迁移历史重复行。
3. 单条回放测试不足以证明修复：顺序重放对原内存去重也能通过，无法复现并发；必须让两个并发请求真实打到唯一约束上。

下一步
- 当版验收：① 两路并发投递同一回调（两个实例/两个连接），断言发货恰好 1 条、两次响应一致且均成功；② 顺序重放同一回调多次，发货仍 1 条；③ 相邻订单/不同事件的回调不被误杀；④ 唯一键冲突路径返回幂等结果而非 5xx（避免支付方继续重试）；⑤ 上线后沿用现有重复发货日志口径观察，不再新增。
- 回滚：约束与表用独立 migration；回滚时回退应用开关并删除约束/表，幂等记录保留做审计不删除。应用层读取去重状态失败时应拒绝处理并告警而非放行（“宁可少发不可重发”），此点需业务确认后写进验收。
- 未来再引入条件：出现第二条同样需要跨实例去重的写路径（退款/库存）且确有重复案例 → 再抽通用组件；确认外部副作用无法同事务完成且对账仍漏 → 上 outbox/MQ；历史重复发货由业务/财务给口径后单独立项。

## R2（原 E45-2）

判断：应实施（限最小范围），不是照单全收。数据库唯一约束 + 幂等记录表是当前证据下正确的跨实例去重方向；回放回归测试方向也对，但必须保留“并发 + 两个实例”两个条件，否则不能作为验收证据。

理由
1. 证据链已经闭合。服务有 2 个实例、去重只在单实例内存、日志显示两次回调并发到达——两个实例各自在自己的内存里判重都会通过。重复发货不是偶发，而是该部署形态下的必然缺口。因此修复必须落在一个跨实例共享、能原子仲裁的地方。现有数据库就是最小选择：业务唯一键 + 唯一约束，插入幂等/发货记录与订单发货状态变更放在同一本地事务；唯一冲突即视为重复，返回与首次一致的成功结果，不再触发发货。不要“先查再插”，并发下仍会穿透；唯一约束才是最终仲裁。前提是两实例确实共用同一数据库（题目未明说，落地前确认）。
2. 方案没写清、但决定成败的两点：幂等键必须是业务唯一键（订单号，或与一次发货一一对应的支付通知 ID），去重应落在“发货”这个业务动作/订单状态迁移上，而不只是回调入口——否则同一订单的两条不同通知 ID 仍可能各发一次。若发货含外部物流调用，本地唯一记录必须先落库再调用，保证只有首个请求发起外部动作；崩溃后的对账补偿延后，不在当版展开。另外，只有“唯一键冲突”才按重复处理，其他写库异常必须照常失败并允许重试，不能静默吞掉发货。
3. 范围只覆盖支付回调→发货链路。不引入 Redis/分布式锁：数据库唯一约束已提供跨实例互斥，再加锁是重复机制，还多一个故障点。不做通用幂等框架、MQ 改造、全量回调重构、复杂状态机/补偿。题目没有丢消息、乱序、跨库、多地域的证据，这些延后。
4. 测试是当前方案最明显的缺口。若“回放”是在同一实例内串行重放，修复前也会通过（内存去重就能挡住），不能复现原故障。必须两个独立应用实例/进程共享同一 DB 并发打同一回调：修复前红（两次发货），修复后绿（一次发货，第二次返回幂等成功）。一条测试可以，但口径必须是这个；再补一条串行重复回调覆盖平台重试。
5. 存量数据与更简替代。已有重复发货记录，建唯一索引前要先查/清理冲突数据，否则迁移会失败；方案未提。若现有发货表/订单状态已有合适的业务唯一行，优先在它上面加唯一约束或条件更新（`UPDATE ... WHERE status='PAID'`），比新建通用幂等表更小；只有没有合适业务记录、或需要保留回调审计时才新建幂等表。二选一即可，不必两套都上。

下一步
当版验收：迁移在预发和生产成功，唯一约束真实存在，并用重复插入验证冲突路径；并发跨实例回归测试先红后绿；观察 2 周（与本次故障窗口同长），重复发货为 0，回调 5xx/超时率不升，唯一冲突按幂等成功处理且有日志/计数；正常单次回调仍只发一次，发货状态和物流单号正确。
回滚：回滚代码，保留幂等表/唯一索引（附加结构，保留无害，避免删数据）；只有索引导致合法写入被拒且无法快速修正时，才备份后删索引。回滚会重新暴露重复发货，只在更严重回归时使用。注意两实例滚动发布期间旧实例仍用内存去重，存在短暂窗口：要么快速全量切换，要么临时单实例/摘流，并在窗口内盯重复发货。
未来再引入：出现“外部发货成功但状态未落、重试丢发货”的证据，再加 PROCESSING 超时/对账补偿；出现多渠道/不同通知 ID 的通用去重需求，再抽通用幂等组件；数据库不共享、跨地域/多库时，才考虑 Redis/MQ/分布式协调；业务出现合法补发/拆单时，幂等键下沉到单次发货请求；有实测数据库争用/吞吐问题再评估队列或锁。

## R3（原 E45-3）

判断：部分实施。
- 应实施：用数据库唯一约束做跨实例、持久化、且与发货写入在同一事务内提交的幂等；幂等记录表是承载该约束的方式之一。
- 改造后再实施：回归测试必须是能并发复现原故障的 red→green 测试，顺序回放不算。
- 不实施或延后：分布式锁、Redis 去重、MQ、回调框架重构、预防性 outbox。
- 单独立项：已发生的 3 次重复发货的追回与影响面排查。

理由
证据已足以定位根因，无需再假设：日志显示两次回调并发到达；去重是单实例内存；服务部署 2 个实例。并发回调落到不同实例时，两个进程的内存集合互不可见，都会判“未处理”，于是各发一次货。这是跨进程共享状态缺失，不是网络抖动，也不是“回调不该重复”——在至少一次投递下，重复回调是常态，必须由消费端幂等消化。
必要机制只有一个：两个实例都能看见、且“检查+写入”原子完成的去重点。数据库是现成的权威共享状态，唯一约束是原生原子操作，不需要新依赖。这是该方案真正正确的部分。
三处缺口决定范围大小：
1. 幂等键未定义（题目未给回调报文结构）。只用 order_id，未来同一订单的合法多次事件（重复支付尝试、部分退款、补发）会被误杀；用回调事件 ID，要先确认回调里有稳定、可重放的事件标识。这是动手前必须确认的第一件事。
2. 原子性边界未说明。唯一约束只有在幂等记录/发货写入与发货副作用同一事务提交时才真正防重。若发货是跨系统外部调用（题目未说明），事务覆盖不了外部副作用：先提交后调用失败会漏发，先调用后提交失败会重发；那时才需要 outbox 或让下游按同一幂等键去重。不能默认它不存在，也不该现在预防性上。
3. 测试形态。“回放”若指把日志里那两条并发回调按并发时序重放，方向正确；若只是顺序重放，旧代码也会通过（内存去重对同实例顺序请求是有效的），拿不到 red→green，不能作为验收证据。
还有一项不在这份方案里、但不该被忽略：已发生的 3 次重复发货如何追回、是否还有其他订单受影响。这属于数据/运营修复，单独立项，不塞进这次代码切片，但也不能当作不存在。
范围：一个纵向切片——回调入口在事务内写幂等记录，唯一键冲突按“已处理”返回与首次一致的结果（不能抛 5xx，否则网关重试会放大问题），发货写入同事务，外加并发回归测试和冲突计数。内存去重可保留为快路径，但不能当正确性保证，也不必为删它扩大改动。
更简单的替代：真正必要的是“一个唯一键”，独立幂等表只是载体。若确认处理链只有一条发货写入且该记录有天然业务唯一键，直接把唯一约束建在发货记录上即可，无需新表；幂等表在“一次回调有多个副作用/需缓存首次结果”时才值得。按“最小能覆盖全部副作用的键”选，不为对称性造表。相比之下，分布式锁/Redis 是更重的替代且更弱：额外依赖、非持久、进程崩溃或锁过期后没有权威记录，替代不了唯一约束。

下一步
当版验收：
- 红：在修复前的提交上跑新并发测试，稳定复现两次发货；绿：修复后同一测试只产生一次发货、一条幂等记录。红证据必须修复前取得，修完补跑通过不算。测试连真实数据库、用真实唯一约束，不用内存 mock 替身。
- 并发口径：两个应用实例（至少两个独立连接/事务）同时提交同一回调，只有一个执行发货，另一个走冲突分支且返回与首次一致的结果，接口非 5xx。
- 混跑窗口：滚动发布期间旧实例不写幂等表，仍是漏洞。要么全量切新版本后复测，要么明确接受并缩短窗口；不能把“新版本已上线”当作已修复。
- 观测：唯一键冲突次数、重复发货告警，上线后持续观察（窗口由团队定，不编数字）。
- 总需求验收看“并发下不再重复发货”的实际证据，不用“加了约束/测试通过”的数量代替。

回滚：
- schema 是增量（新表 + 唯一索引），回滚代码即可，表保留不影响旧代码，不做破坏性迁移。
- 若唯一键误杀合法回调，先改键/摘约束再回滚代码，避免正常支付被卡住。
- 回滚判据：冲突分支出现非预期拒绝，或发货成功率下降。

延后部分的再引入条件：
- 发货含不可事务化的外部调用（有证据）→ outbox/本地消息表，或要求下游按同一幂等键去重。
- 同一订单存在合法多次事件 → 幂等键升级为事件级。
- 唯一约束成为写热点/锁竞争（有实测）→ 再谈分片键或其它协调。
- 出现跨系统统一回调治理需求 → 才谈通用回调框架，不从这次 3 次事故直接外推。

## R4（原 E46-1）

## 判断

部分实施。本版只实施“导出路径的有界内存或分批流式改造”；“通用任务编排平台”和“配置中心”本版不实施，予以延后。

## 理由

- 题目给出的确定证据只有：导出偶发 OOM，已复现 3 次，3 次都是把 200 万行一次性全量载入内存；用户要求是“修复导出失败”。这足以支持对导出执行路径做内存改造，但不足以支持平台化。
- 必要机制是“有界内存导出”，而不只是“分批”这个说法：服务端游标或 keyset 分页（避免大 OFFSET 和一次性 list）、固定上限的批大小、边读边写输出（流式响应、临时文件或压缩流）、背压与异常清理；同时确认 ORM、驱动、序列化层没有把结果集再次整体缓冲。验收要证明峰值内存有界，而不是只证明“能跑”。
- 通用任务编排平台与配置中心解决的是调度、重试、依赖、并发配额、跨环境配置等另一类问题；题目没有给出这些需求的实际用例、失败样本、现有机制不足的证据，也没有量级、成本、运维评估。“以后导出任务会变多”是预测，不是当版验收证据。现在引入会把一个局部可逆修复变成跨模块基础设施项目，增加新的故障风险和交付周期，且不直接消除已复现的 OOM 根因。应先查是否已有等价的任务调度或配置机制；若已有，平台化更无必要。
- 替代方案比较：A 有界内存流式或分页导出，最小、直接、可回滚；B 提高内存或扩容，拒绝，因为只是推迟 OOM，3 次复现已说明全量载入不可持续；C 异步导出任务落临时文件，若还有请求超时或长任务需求才考虑，当前无此证据；D 通用平台，本版拒绝。因此 A 是当前证据下的最小充分方案。

## 下一步

当版验收：
1. 用原入口、原筛选条件、200 万行规模复现原失败场景，至少一次真实规模回归；导出成功，行数与源查询计数一致，关键字段抽样或校验和一致。
2. 记录峰值内存、批次数、耗时和失败原因，证明内存不随总行数线性增长；阈值按现有部署内存基线确定，不在此编造具体数字。
3. 覆盖取消、超时、下游断开、异常回滚和临时文件清理；小数据量导出无回归。
4. 代码审查确认没有全量 `list()`、`fetchall()`、全量 workbook、全量字符串拼接等二次缓冲；若 ORM 仍缓冲，需换游标或驱动级流式。

回滚：保留旧导出路径或特性开关；出问题可一键切回或回退版本；不引入不可逆 schema 变更；临时文件有清理策略。

未来再引入条件：出现多个真实导出任务且确有排队、重试、依赖、并发限制、统一观测需求；或配置需要跨环境动态变更和审计，且至少有两个真实消费方；同时能给出当前简单机制不足的失败样本和成本评估。届时优先复用现有调度或队列，而不是自建“通用平台”。

## R5（原 E46-2）

1) 判断：部分实施

实施：把导出链路改成读写两端都有界内存的分批流式导出，同时保留现有导出入口与调用方式。
不实施（本版延后）：通用任务编排平台、配置中心。它们与本次已经复现的 OOM 没有因果关系，把故障和它们绑在一起，相当于借故障扩大范围。

2) 理由

现有证据只支持一件事：3 次 OOM 都发生在把 200 万行全量载入内存时，用户要求修复导出失败。因此必要的修复是消除全量驻留，范围应限制在导出路径内部。

但题目也暴露了证据缺口，方案不能直接照单全收：
- “3 次都是全量载入”只是对故障现象的归纳，不是内存剖析。峰值可能来自保存结果集的 List，也可能来自写文件端（例如 XLSX 工作簿模型要求全量驻留）。因此“流式”必须同时覆盖读端和写端，并用实测确认；只改 JDBC fetch size 可能仍然 OOM。
- 题目没有提供内存上限、行宽、输出格式（CSV/XLSX）、并发导出数、超时限制。这些决定批次大小和写入实现，属于实施前要补齐的最小信息，不需要做成平台。
- 编排平台和配置中心的理由是“以后导出任务会变多”，这是未来假设：题目没有第二个任务类型，没有并发、重试、断点续传、跨团队复用的实例，也没有现有调度或配置方式失败的样本。这是“为以后可能新增机制”的过度防御：新引入调度、状态存储、重试、权限和观测，复杂度和新增的故障面远超一个导出任务。应先说明已有的定时触发、应用内调度方式、现有配置方式为何不够；目前没有可复现失败样本，就不应加。
- 候选比较：A 现有链路内分批流式（最小、可逆）；B 流式 + 异步任务与进度（仅在出现请求超时或需重启续跑的实证后再做）；C 通用编排平台（本版不选）。更简单的替代就是 A。可先向用户确认是否真的需要一次性全量 200 万行，还是可分片或按时间范围导出。这是产品层更省成本的替代，但不能替代修复本身。

本版必要机制：
- 读：服务端游标或分批 fetch，固定批次，不把结果集聚成 List。
- 写：CSV 或流式 XLSX（如 SXSSF 类）逐批 flush，避免工作簿全量驻留；若输出格式要求普通 XLSX 且库不支持流式，先与用户确认格式或换流式实现。
- 固定内存上界并实现背压；异常或取消时关闭游标、删除半成品临时文件，不把不完整文件当作成功。
- 语义不变：列、顺序、编码、转义、null、行数；现有调用方与入口不变。
- 核实长读事务和连接占用（只读连接、fetch size、语句超时），避免修好 OOM 却拖垮连接池或造成长事务。
- 可观测：批次进度日志、峰值内存记录。

应延后：通用任务编排（调度、DAG、重试、状态存储、UI、配额）、配置中心（动态配置、审计、灰度、多环境）、多任务并发治理。等出现触发条件再立项。

3) 下一步

当版验收（按可证伪口径，不按“跑通一次”）：
- 复现口径：在与 3 次失败相同的数据与环境上导出 200 万行，成功且输出完整；记录修复前后峰值内存。
- 证伪点：对比同一查询的小窗口（如 20 万行）与 200 万行的峰值内存，二者应接近、不随行数线性增长；若仍线性增长，说明流式未真正成立，不能验收。
- 正确性：行数与源查询一致；列、顺序、编码、转义、null 与旧实现比对（小窗口全量比对，200 万行做抽样字段校验和）；文件可被下游正常打开。
- 边界：空结果、超宽行、DB 中途报错、用户取消——均不产生“成功”的半成品，临时文件清理、连接释放。
- 回归：现有导出入口和定时任务不变；DB 连接数与慢查询指标不恶化。

回滚：
- 改动收敛在导出实现内部，保留旧路径开关或独立可 revert 的提交；无 schema、数据迁移。回滚即切回旧实现或回退版本，验证旧导出仍可用；先单环境或小流量验证再全量放开。

未来引入被延后部分的条件（满足其一且有真实样本，再走 ff-prove/小原型，比较自建 vs 现有调度或队列）：
- 出现第二个独立的导出或后台任务类型，且确实需要统一调度、重试、恢复或配额；
- 出现“请求超时、进程重启需续跑、多任务并发争抢资源”的实际事故样本；
- 配置需要不发布即变更，且有审计、多环境、多租户要求，现有配置方式已被具体失败样本证明不够。
在满足这些条件前，不按“以后会变多”建设通用平台。

## R6（原 E46-3）

**判断：部分实施。** 只实施“分批/流式导出”这一必要修复；“通用任务编排平台 + 配置中心”本版不实施，延后。

**理由**

1. 证据只支持一个结论：OOM 已复现 3 次，成因明确为“一次性把 200 万行全量载入内存”；用户诉求是“修复导出失败”，没有提出任务变多、统一调度或配置管理的需求。修复点就在这条导出路径的内存占用上，范围应止于该路径，不应借机升级为平台建设。
2. 必要的机制（当版）：
   - **有界读取**：服务端游标或 keyset 分页，禁止 list 全量，配背压（读多少、写多少）；
   - **有界写出**：边读边写（流/临时文件），内存不随行数线性增长；
   - **失败语义**：中途失败不留下半成品被当作成功文件，临时资源释放，进度与错误可观测；
   - **回归证据**：同一复现数据集上导出成功，行数与关键字段校验和与全量查询基线一致，峰值内存有界。
3. 不应随本次实施：编排平台与配置中心建立在“以后导出任务会变多”这一纯假设上。题目没有任务数量、并发、调度/重试/优先级、多环境配置差异的任何证据，也没有“现有机制不够用”的可复现失败样本。按 L2，没有失败样本就先不加机制；两者还会引入新的部署单元、状态存储与故障面，把单点内存问题升级为平台迁移，验证成本和风险与收益不匹配。按 L3，方案里也没有与更简单替代的比较。
4. 候选比较：A 仅流式修复（推荐）；B 抽出可复用的“导出作业”模块（有界内存 + 进度/取消，仍是进程内、无平台）；C 通用平台 + 配置中心。当前证据只支持 A。B 要等出现第二个同类导出且共享同一失败模式；C 要等出现多类异构后台任务（排队/重试/限流/优先级）与多环境配置漂移的真实痛点，且 A/B 无法覆盖。

**下一步**

- **当版验收**（回到总需求，不用“改动完成”代替）：用复现 OOM 的同一入口、同一数据集跑真实导出；成功且行数、关键字段校验和与基线一致；观测进程峰值内存，确认不随行数线性增长（具体阈值题目未给，实施前与用户/运维按机器约定）；注入中途失败，确认无半成品文件、临时资源清理、错误可见；并发导出场景行为不劣化或明确限制。
- **回滚**：改动限制在导出路径内，不新增服务、状态库或表结构，回滚即回退该次发布；若保留新旧两条路径，用开关控制、默认新路径，异常时切回并记录（旧路径本身会 OOM，切回只是止血，不是修复）。不把平台或配置中心作为回滚依赖。
- **再引入延后部分的条件**（需证据，不是时间表）：后台任务数量/类型增长到单点维护成本明显（出现排队、重试、优先级、限流需求）；出现 A/B 覆盖不了的具体故障（并发打满数据库、任务丢失、配置漂移导致环境不一致）；配置出现多环境/多租户差异且变更频繁。满足后先做方案比较与小范围试点，再决定是否平台化。

**实施前需确认的未知**（不改变范围判断）：内存上限与机器规格、行宽/大字段情况、导出格式与下游消费方式、并发导出数量、数据库是否支持服务端游标——这些决定选游标还是 keyset 分页，但不改变“只做流式修复”的结论。
