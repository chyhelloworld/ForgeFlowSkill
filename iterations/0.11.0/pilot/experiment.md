# 云端合成稽查试点：能否看出任务全勾选仍未兑现目标

## 要回答的问题

主干视图是否帮助读者更快发现：任务局部完成，但原目标所需的确认权限和端到端证据仍缺失？这是可用性假设，不因画面能打开就算验证。

## 材料与边界

- [architecture.md](architecture.md)：同一文档里的目标、拟议职责、必要缺口与主干投影。
- [intent-view-links.json](intent-view-links.json)：将 R1、模块、原任务绑定到该文档；版本标签与投影一致。
- [合成任务](openspec/changes/synthetic-inspection/tasks.md)：刻意设置 2/2 勾选，但两项仅为局部展示，不覆盖权限和真实主路径。

不连接数据库、账号或真实车辆材料，不声称已经实现稽查产品。任务勾选、候选设计、证据有效性、用户接受分别观察。此试点不新增阶段或门禁，不向原任务写状态。

## 显式生成

在 FF 源码根执行以下命令，工作区是本例独立目录，不是仓库的实际业务计划：

```bash
node dsh-plugin/generate-board.mjs --workspace iterations/0.11.0/pilot --intent intent-view-links.json --architecture-graph architecture.md --html --write
```

`--architecture-graph` 显式选择同一 `architecture.md`，索引 `architecture_ref` 也须绑定它；两者相对工作区/指定的 `--source-root` 解析。`source_revision` 必须非空并与模型一致。`--html --write` 仅输出本例 `.forgeflow/architecture-board.html`（生成 DSH 面板 JSON 快照时去掉 `--html`），不修改需求、任务、批准或验收。重复生成只更新投影；未显式接入时不改变原默认视图。

## 对照步骤与记录

1. 文字组只看同一份目标、职责、缺口和任务文本；主干组看其只读投影，信息量保持一致。交换顺序再看一次，记录熟悉材料造成的影响，不把第二次更快直接归因于图。
2. 不先告诉读者答案，请其指出原目标、当前路径、漏掉的必需条件、未确认扩展、下一步应验证什么，并定位依据。
3. 记录找到权限缺口和端到端缺口的用时、漏判项、误认为已完成的次数、能否回到原文。折叠/聚焦后重复检查，两个必要缺口应仍可被发现。
4. 反例检查：显示 2/2 任务勾选时，是否仍明确设计候选、证据缺失、未验证用户接受？不能出现“业务就绪/已验收”的推断。版本不匹配、引用断链或关系不合法时，应显示不可用/缺口，不以旧图继续声称有效。
5. 最后将结果写成“问题→进度→观察→结论→下一步”，分别记录生成器测试、浏览器渲染和读者试用。自动测试只能证明对应规则，不能代替真人判偏差能力的证据。
