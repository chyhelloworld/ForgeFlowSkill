ForgeFlow 九接口工作流中文使用手册

版本：0.4.0-rc1 候选版 · 2026-10-15

这份手册说明如何用九个职责单一的 FF 技能，把新想法或已有半成品推进成可验证、可审查、可交接的项目切片。核心路线是目标澄清 → 规格 → 实施票据 → 独立计划审核 → 实现 → 独立主流程与代码审核 → 验收与交付。已有项目先只读接手，再按缺口选择最短路径，不要求九个技能全部运行。

本版本是技能说明与配套工作流的候选包，不宣称已在任何宿主完成安装、自动路由、工具调用或真实项目端到端集成测试。文中“用 ff-…”是自然语言调用示例；能否使用斜杠命令、如何载入技能，由宿主能力和安装方式决定。

先选对入口

  • 新项目，目标尚不清楚：用 ff-grill。目标已明确确认：直接让 ff-spec 复用目标。
  • 已有代码、半成品、换人接手或暂停后恢复：先用 ff-intake，只读核对实际状态。
  • 已有有效规格，但没有可执行票据：用 ff-plan，然后做独立 plan 审核。
  • 规格、票据、计划审核与实施条件都有效，且已有权限：用 ff-implement 继续最小切片。
  • 只是准备 PR、验收说明或交接：用 ff-deliver 核对当前版本证据与授权，缺什么回到对应责任。

“材料齐全”“实施就绪”和“已获授权”是三件不同的事。没有文件不一定必须新建文件；文件存在也不代表它仍然有效。

九个技能分别做什么

技能什么时候用主要产物或结果可以跳过或复用的条件
ff-intake旧项目接手、暂停恢复、状态不明只读状态报告；目标、规格、票据、代码、测试、脏状态的对账；下一责任新项目且没有任何待接手状态时可不运行；旧报告须核对版本及环境才能复用
ff-grill用户、问题、目标、范围或关键取舍不清澄清后的目标、非目标、约束、待决问题与确认状态已有明确且当前有效的确认，不重复盘问
ff-spec目标明确，但缺产品/功能规格或规格过期主流程、行为、边界、错误路径、验收标准和追踪关系当前规格已覆盖本次目标和边界，可复用
ff-design关键视觉或交互方向需要比较、选择可评审设计候选、选择理由、状态与设计约束无相关视觉未知，或已有有效设计时跳过
ff-prove技术可行性、真实入口或环境能力有关键未知有界实验、结果、证据、限制与是否可继续的结论已有同等环境和版本的有效证据时复用；不把猜测当验证
ff-plan有规格，但需要实施拆解、重排或补票据可执行切片/票据、依赖、测试策略、证据要求与回滚考虑有效票据已覆盖当前规格且独立计划审核仍有效
ff-implement已获准且就绪的票据需要实现代码/配置/相关文档变更、测试结果、版本证据和检查点切片已实现且当前证据充分时不重复写；直接核对审核和交付缺口
ff-review计划准备实施，或切片/集成已可验证独立计划审核、目标与真实主流程审核、代码审核，各自结论与问题仅能复用范围、版本、依赖未变且适用的独立审核；不能以自评冒充独立审核
ff-deliver当前成果需要验收、PR、阶段交接短验收说明、证据索引、偏差/未验证项、人工接受状态与授权范围内 PR尚未达到交付门槛时可给明确受阻交接，不把受阻说成完成

一个技能只处理自己的责任。ff-spec 不写实现计划代替规格；ff-plan 不包办实现；ff-implement 不把自测当独立审核；ff-deliver 不充当全能开发器。

新项目如何从想法走到交付

第一步 让目标足以作决定

使用 ff-grill 只追问会改变方案的重要问题：谁会用、解决什么问题、成功怎样判断、本轮不做什么、时间预算和权限有什么限制。明确决策人与尚待确认的假设。已有确认就引用，不重新问一遍。

示例提示词：请用 ff-grill 澄清一个团队预约工具的首个可交付切片。先确定目标用户、核心场景、成功条件和非目标；只问会改变实现方向的问题，先不要写代码。

第二步 把目标写成可验收规格

使用 ff-spec 记录用户行为、真实主流程、状态变化、边界和错误路径，以及可观察的验收标准。规格回答“做什么、为什么、怎样算满足”。记录需求标识，方便追踪到票据、测试、审核证据。

示例提示词：请用 ff-spec 把已确认的预约目标形成规格。覆盖创建预约、冲突处理、取消、权限边界和失败提示，并给出可操作的验收标准。复用现有项目文档路径。

有重要视觉未知时使用 ff-design；有技术或真实环境未知时使用 ff-prove。它们的结论要反馈到规格；必要时回到 ff-grill 重新决定取舍。它们是有条件的支线，不是每个项目必须经过的仪式。

示例提示词：请用 ff-design 比较两个移动端预约交互方向，说明各自取舍，等我选定后把选择反馈到规格。

示例提示词：请用 ff-prove 验证现有日历接口是否支持重复预约和冲突检测。限定实验范围和停止条件，保留真实请求结果，区分已验证、受阻与未知，不把原型直接当正式实现。

第三步 从规格到票据 再独立审核计划

ff-plan 把规格拆成能独立验证的最小切片。每张票据应能找到目标/规格依据、实施范围与依赖、验收标准、测试与证据要求、风险、完成条件和必要的回滚处理。跨切片的集成路径也要明确。

示例提示词：请用 ff-plan 根据当前规格拆分实施票据，按最小可验收主流程排序。为每片列出依赖、验证命令或手工步骤、证据位置与阻塞条件，不开始实现。

随后用独立评审者执行 ff-review 的 plan 审核。评审者检查计划是否覆盖目标、主流程和风险，是否有真实可用的验证入口，是否过大、遗漏依赖或把假设写成事实。审核失败回到计划；发现需求矛盾回到规格；修订后对受影响范围复审。

示例提示词：请安排独立评审者用 ff-review 审核这份计划，review_kind=plan。重点检查需求覆盖、票据可执行性、真实入口、验收可操作性和依赖风险。不要写实现代码。

这里的 review_kind 是责任选择语义，并非已验证的命令行参数。计划审核发生在实施前，不能等到项目末尾才补。

第四步 按获准切片实现与验证

ff-implement 先核对计划审核、切片 readiness、当前权限和工作区，再执行实现、相关测试与文档维护。只推进已就绪且获准的部分；缺口只阻塞依赖它的部分。保持切片小而完整，避免一次改动跨越大量无关需求。

示例提示词：请用 ff-implement 实施已审查的预约创建切片。仅在已确认范围内修改，保留现有未提交改动，运行对应测试，把证据绑定当前版本。发现规格缺口先标出影响并回到相应责任。

第五步 独立检查真实主流程和代码

对相关切片与集成执行 ff-review 的 goal-mainflow 与 code 两类独立审核。主流程审核从真实用户入口走通用户目标，识别占位页面、mock 数据、未接入按钮和不可达结果。代码审核检查实现风险、可维护性、相关回归与测试可信度。实施者自测有价值，但不是独立审核。

示例提示词：请由独立评审者用 ff-review 检查当前版本，分别给出 goal-mainflow 与 code 结论。主流程从真实入口验证预约创建与冲突处理；代码审核检查状态一致性、失败路径和回归风险。列出证据与未运行项。

审核发现实现缺陷，回 ff-implement 修复、复验，再复审；发现目标或规格偏移，回 ff-spec，分析哪些票据与证据失效。不用不相关的全量重跑代替有依据的影响分析。

第六步 验收与交付

ff-deliver 整理当前版本、访问入口、操作步骤、期望结果、证据、偏差与未验证项，并单独记录人工接受。没有用户反馈时写“待接受”；技术通过不代表用户已经接受。交付可分阶段，不必把未完成部分藏起来。

示例提示词：请用 ff-deliver 整理这一切片的短验收说明和 PR 草稿。列出版本、真实入口、验证结果、独立审核、风险、未验证项和人工接受状态；只有已有仓库授权覆盖时才执行提交 PR。

只有仓库采用 PR 工作流且已有授权时才准备或提交 PR；不采用 PR 工作流的项目可以交付文件、证据包与交接说明。PR 是代码审查与交付载体，不是规格文档，也不是自动合并、部署或发布的授权。若仓库允许未验收草稿 PR，可如实标明草稿与待验收状态；不得把它称为最终验收完成。

旧项目或半成品项目怎么接手

先只读盘点

ff-intake 读取现有目标与确认、规格、票据/计划、代码、测试结果、分支/提交、未提交与未跟踪文件，以及检查点和仍在执行的操作。报告“已知什么、缺什么、哪些材料失效、下一步该承担哪项责任”。Intake 本身不写文件、不重置工作区、不替别人改计划。

示例提示词：请先用 ff-intake 只读接手这个半成品。对账目标、规格、任务、代码、测试、分支和脏工作区，区分有效、过期、缺失、未知。指出下一步应进入哪个技能，先不要修改文件或重复运行可能有写入副作用的操作。

四种明确分流

  1. 目标缺失或不清楚：进入 ff-grill；目标清楚后核对规格，再补必要的计划与审核。
  2. 目标清楚，但规格缺失或过期：进入 ff-spec；有设计或技术未知再选 ff-design / ff-prove，结论回写规格。
  3. 规格有效，但票据缺失或过期：进入 ff-plan，随后执行独立 plan 审核。
  4. 规格与票据都有效：复用现有产物。核对独立计划审核、实施条件和授权；通过后进入 ff-implement，不能因“文件都在”直接开工。

任何分支遇到 unknown 都先核实，不能把未知等同于 valid。若实现已经完成，则按实际缺口进入验证、独立审核或 ff-deliver，不为走流程重复实现。

示例提示词：若现有规格和票据仍有效，请不要重写它们；只核对受影响的审核、测试证据和授权。选择可继续的最小切片；不满足就绪条件就报告具体缺口。

暂停与恢复

在已有项目约定的位置保存检查点，至少包含当前版本与脏状态、已完成和部分完成产物、运行中操作、已知失败和阻塞、有效证据、下一步以及权限边界。敏感凭证不进入检查点。

恢复先用 ff-intake 对账实际状态。确认旧命令是否结束、外部操作是否产生结果，再决定是否续跑，避免重复写入或重复提交。重新检查环境、权限、依赖与证据有效性。检查点是可恢复信息，不承诺自动唤醒、进程持续存活或宿主跨会话状态保留。

小修怎么保持轻量

范围明确、风险低的小修可以使用内联规格与内联票据，不强制制造一整套新文档。例如：“修正移动端按钮被遮挡”可以用简短记录说明受影响入口、期望行为、非目标、改动边界、回归步骤和完成条件。

可跳过没有实际未知的 Grill、Design、Prove；已有有效内容直接复用。规格与计划的职责仍保留，独立计划审核可以很短，相关主流程与代码审核也按风险缩放。轻量不代表省掉验收、权限、验证、独立性或变更影响记录。先保护已有修改，再实施。

示例提示词：这是一个明确的小修。请用内联规格和票据记录目标、范围、验收及验证，做与风险相称的独立计划审核，再实施和独立复核。不要扩展成无关重构。

变更时哪些内容失效

需求变更先确认其目标、范围、预算与权限是否仍在授权内。对获准变更分析受影响的规格条目、票据、测试、审核、证据和人工接受；将受影响内容标为 stale 或待复验，保留未受影响的有效证据。不要把旧版本的通过或用户接受自动继承给新版本。

例如把“单人预约”改成“多人共同预约”，可能影响冲突规则、权限、数据模型、主流程、测试与用户验收；纯文案修正可能只影响截图和相关验收，不一定使全部后端测试失效。范围扩大或涉及新权限时重新取得必要授权。

材料有效性统一用 valid / stale / missing / unknown。测试和验证结果统一用 PASS / FAIL / NOT_RUN / BLOCKED / N/A；N/A 要说明为何不适用。未测量的 CRAP 指标记为 NOT_MEASURED，不用猜测填值。不运行或受阻的检查不能算通过。

产物如何放置和追踪

优先复用项目已有的文档、规格、任务、测试和审核位置，不强制所有仓库改用同一组文件名。建议保留从目标 → 规格条目 → 票据 → 实现版本 → 测试 → 独立审核 → 人工接受 → PR/交接的可追踪关系。

  • Intake：只读报告放在当前回复或宿主已有的只读报告出口；不因接手擅自落盘改项目。
  • 目标与规格：区分已确认、待确认和假设，保存本次范围与非目标。
  • 设计/实验：保留选项、结论、适用环境、限制以及反馈到的规格条目。
  • 票据：每片有范围、依赖、验收、验证和状态，不用 PR 描述倒推需求。
  • 实现与验证：记录版本、命令/步骤、实际结果、证据位置及未验证项。
  • 独立审核：区分 plan、goal-mainflow、code，记录评审者独立性、覆盖范围和复审状态。
  • 交付：单列技术完成、用户接受、PR 状态和发布权限，方便接手而不混淆。

包内 ROUTING.md 是轻量路由说明；共享状态契约位于 skills/ff-intake/references/state-contract.md。它们帮助选择下一责任，不强制固定顺序，也不提供未经验证的宿主调度能力。

授权边界和完成判断

实施就绪只说明材料、依赖和验证条件足够，不扩大授权。已有工作计划范围内可以按当前授予权限执行开发、测试、相关文档和计划维护、工作分支提交；仍须遵守仓库规则和平台确认要求。主分支合并、发布部署、额外付费、扩大持久访问及安全敏感设置变更不因技能流程自动获得许可。

每个阶段的状态要可核查：计划通过不等于代码通过；代码通过不等于真实主流程通过；技术完成不等于人工接受；PR 创建不等于合并或上线。阻塞时报告具体缺口、影响范围和下一步，不把未知变成承诺。

离线文件怎么使用

  • FF-中文使用手册.md：可编辑正文。
  • FF-离线图文手册.html：内嵌两张 SVG、样式与目录筛选脚本，直接在浏览器打开；无需联网或额外字体下载。
  • diagrams/new-project-workflow.svg 与 .png：新项目流程矢量版与图片版。
  • diagrams/existing-project-workflow.svg 与 .png：已有项目接手流程矢量版与图片版。
  • 两个同名 .drawio：在兼容 draw.io 的编辑器中打开，可编辑节点、文字、连接线、标题、分支标签和页脚说明。

图中的“就绪”“复审通过且已获准”等文字是流程决策条件，所有图格式与 HTML 均保留。箭头是交接语义，遇到失败或变化应按节点说明返回相应责任，而非承诺自动执行。
