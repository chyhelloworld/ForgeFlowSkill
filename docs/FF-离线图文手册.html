ForgeFlow 十二技能工作流中文使用手册

版本：0.5.0-rc1 候选版 · 2026-10-15

这份手册说明如何用九个主流程职责与三个可选执行方法，把新想法或已有半成品推进成可验证、可审查、可交接的项目切片。核心路线是目标澄清 → 规格 → 实施票据 → 独立计划审核 → 实现 → 独立主流程与代码审核 → 验收与交付。已有项目先只读接手，再按缺口选择最短路径，不要求十二个技能全部运行，更不是十二个必经阶段。

本版本是技能说明与配套工作流的候选包，不宣称已在任何宿主完成安装、自动路由、工具调用或真实项目端到端集成测试。文中“用 ff-…”是自然语言调用示例；能否使用斜杠命令、如何载入技能，由宿主能力和安装方式决定；技能文件名不保证已注册同名斜杠命令。

本版增加规格生命周期，技能仍为 12 个。打开项目时先看当前有效规格、活跃变更及其状态，再按需查历史；不必阅读全部旧提案才能知道产品现在承诺什么。规格合入是更新文档基线，不代表 Git 主分支合并或发布。

先看当前承诺 再看本轮变更

当前有效规格、活跃变更与归档历史各负其责，只有当前有效规格代表已生效承诺。活跃变更是本轮拟增加、修改或移除的差异，不能默默覆盖基线；归档用于追溯，不作为另一份现行规格。

  • 当前有效规格：保留稳定的需求 ID、可观察行为与验收标准，以及生效的版本和来源。
  • 活跃变更：明确基于哪版规格、改哪些需求、为什么改、用户确认依据、任务以及验证证据。任务和证据都追踪到需求 ID。
  • 归档历史：保存已完成或已取消变更的原因、结果和追溯关系；取消的变更也可以归档，但绝不合入当前有效规格。

新项目先建立确认过的基线

先由 Grill / Spec 确认目标、范围和验收，给需求稳定 ID，再建立当前有效规格。不要把尚未确认的想法当成基线。初始基线说明已认可的产品承诺，不声称已有实现或测试。随后把实施任务及证据挂到对应需求；新增或改变承诺时使用活跃变更。

已有项目先读三处 再决定下一步

Intake 只读核对当前有效规格、活跃变更和必要的归档记录，同时核对代码、任务、版本与脏状态。没有受控基线时先报告缺口；有权限的 Spec 阶段才整理并确认基线，不在只读接手时自动迁移。旧提案中的内容不因文件存在就成为当前承诺。

验证 接受 合入与归档分别记录

verified 表示所要求的验证证据已具备；accepted 表示有明确的人工接受依据（本工具写入该状态时同时完成规格合入）；archived 表示变更已进入历史记录。verified ≠ accepted ≠ archived。技术绿灯、PR 创建、交付说明和暂停检查点都不能自动补上人工接受。

被接受的变更只有通过基线一致性、需求冲突、任务和证据等门槛后，才能把差异合入当前有效规格，再归档。基线已变化或同一需求存在冲突时阻塞合入，先回到 Spec 分析影响并重新确认受影响内容；不能静默覆盖、直接把旧证据算成新证据。取消路径记录取消原因与依据后归档，保留基线不变。目录移动本身不能证明这些门槛已经满足。

示例提示词：请用 ff-spec 以当前有效规格为基线，为多人预约建立一个活跃变更。给出新增、修改、移除的需求 ID、影响分析、验收与确认状态；不要直接改成已生效规格。计划、实施与验证均引用这些需求和变更版本。

示例提示词：请用 ff-deliver 分别列出本轮技术验证、人工接受、规格合入及归档状态。检查基线是否过期、是否存在需求冲突；缺少接受依据就保持待接受。若取消，记录原因并走不合入的归档路径。

暂停时交接真实的生命周期状态

Handoff 除已有的代码与命令状态外，还交接当前有效规格的版本、活跃变更 ID 与状态、未完成任务、证据版本、人工接受依据、合入或归档是否实际发生、冲突和下一步。只写已经发生的事实。Intake 恢复时逐项核对真实文件和状态，不把“计划归档”写成“已经归档”，也不重复执行结果不明的操作。Mode 0 仍只在当前回复交接。

小修仍按风险缩放：可用简短内联规格与任务；若触及受控规格，则保留稳定需求 ID、变更依据和必要追踪，不因改动小而跳过接受或冲突门槛。没有新增技能，也不要求安装 OpenSpec CLI。

0.5.0 的实际文件与工具

包内工具为 tools/spec_lifecycle.py，仅使用 Python 标准库，不依赖 OpenSpec CLI。按实际获准任务选择是否采用持久化生命周期；简单小修允许保留等价的内联记录，不强制新建 JSON。采用此工具时，项目的 .forgeflow/spec-state.json 是唯一权威规格状态源，也是此工具唯一写入的规格状态文件，schema_version 为 1；在一个文件内原子更新以下三部分。既有规格文件可作为说明或来源，但应明确映射到此基线，不能同时维护两份相互冲突的现行承诺。

部分主要字段阅读目的
currentversion 与 requirements；需求由稳定 ID 映射到含 text 的对象当前有效承诺
active以变更 ID 索引，含 baseline_version、version、status、delta、tasks、evidence、acceptance 与 history本轮变更与尚待归档的终态
archived已接受、取消或拒绝的变更快照与 archive_reason按需追溯

delta 每项含 requirement_id、显式 old / new、why 和 confirmation_ref；新增的 old 为 null，移除的 new 为 null。任务和证据用 requirement_ids 关联受影响需求，用 change_version 绑定本轮版本。修改差异时递增变更 version，并重新检查、更新任务及证据，不能只改版本号伪造有效性。证据还须有实际 ref 与 result。此最小工具的证据结果只接受小写 pass / fail；完整的 PASS / FAIL / NOT_RUN / BLOCKED / N/A 报告仍保留在验证记录中，未运行或受阻不能伪装为 pass。

工具支持以下真实命令。从技能包根目录运行；PROJECT 替换为项目目录，CHG-ID 替换为真实变更 ID，引用和原因替换为已核实内容。这些是用法示例，不表示已经在你的项目执行：

  • python3 tools/spec_lifecycle.py validate PROJECT：只读检查结构、引用覆盖和版本一致性。
  • python3 tools/spec_lifecycle.py apply PROJECT CHG-ID --acceptance-ref RECEIPT_REF：RECEIPT_REF 必须与当前变更中已核实的 acceptance.ref 一致，不能随便填一个非空引用。仅在变更为 verified、基线仍有效、old 值匹配、覆盖检查满足且接受回执与当前变更/基线/证据版本匹配时执行；调用者先核实真实人工接受和权限。工具将接受依据、accepted 状态、applied_version 与当前规格更新一起写入。accepted 在本工具中意味着已接受并已合入规格，不能预先手填此状态来冒充合入。
  • python3 tools/spec_lifecycle.py archive PROJECT CHG-ID --reason REAL_REASON：仅允许 accepted / canceled / rejected 终态；移动到 archived 并保存原因，不改变 current。archived 是存放位置，不是 status 的枚举值。

首次建立 .forgeflow/spec-state.json、新增变更、维护任务或记录验证结果，是授权范围内的正常文档/开发工作；当前没有 init、propose、verify 或 cancel 命令，不要编造调用方式。先参考包内规格状态契约与示例，确认初始基线，保存后用 validate 检查。取消或拒绝需真实依据，维护相应状态后再执行 archive；不能把已合入变更改成 canceled 来撤销生效规格，需要新建反向变更。

人工接受回执保存在当前变更的 acceptance 中，含 ref、change_id、change_version、baseline_version 和 evidence_version。其中 change_id 必须等于操作的变更 ID，baseline_version 等于当前基线；change_version 与 evidence_version 都必须等于当前变更的 version（正整数），同一修订号绑定差异、任务和证据。缺失回执、错配引用或过期版本均不得合入。用户对旧版本的接受不能自动迁移到修订后的变更；确认依据应能核对到当前范围、版本和证据。

失效证据和旧接受回执保存在可选的 history 数组，每项含 version、reason、evidence、acceptance，用于追溯；不能留在当前有效 evidence / acceptance 中冒充现行依据。保留失败或过期历史，不等于它们仍能支持当前 verified 或 apply。工具不会语义核验 history 中的陈旧记录；不得把历史项提升为当前证明。

工具输出 JSON 的 passed 只表示该结构检查或状态写入完成。接受回执的版本匹配也不是身份认证。它不运行测试、不认证接受引用、不判断任务是否真正完成，也不证明独立审核、业务目标或宿主集成通过。真实证据与人工门槛仍由对应技能和执行者负责。并发写入受锁保护；遇到锁或结果不明先核对实际状态，不直接删锁重跑。

先选对入口

  • 新项目，目标尚不清楚：用 ff-grill。目标已明确确认：直接让 ff-spec 复用目标。
  • 已有代码、半成品、换人接手或暂停后恢复：先用 ff-intake，只读核对实际状态。
  • 已有有效规格，但没有可执行票据：用 ff-plan，然后做独立 plan 审核。
  • 规格、票据、计划审核与实施条件都有效，且已有权限：用 ff-implement 继续最小切片。
  • Bug 根因不明：用 ff-diagnose 先定位，再把修复交给 ff-implement；已知原因的小修可内联诊断。
  • 实施中的可测试业务行为：在 ff-implement 内用 ff-tdd，逐条完成 red → green；重构先走 Review 与范围门控。
  • 即将暂停、换模型或换会话：用 ff-handoff 写出站检查点；接收方再用 ff-intake 只读对账。
  • 只是准备 PR、验收说明或成果交付：用 ff-deliver 核对当前版本证据与授权，缺什么回到对应责任。

“材料齐全”“实施就绪”和“已获授权”是三件不同的事。没有文件不一定必须新建文件；文件存在也不代表它仍然有效。

十二个技能分别做什么

技能什么时候用主要产物或结果可以跳过或复用的条件
ff-intake旧项目接手、暂停恢复、状态不明只读状态报告；目标、规格、票据、代码、测试、脏状态的对账；下一责任新项目且没有任何待接手状态时可不运行；旧报告须核对版本及环境才能复用
ff-grill用户、问题、目标、范围或关键取舍不清澄清后的目标、非目标、约束、待决问题与确认状态已有明确且当前有效的确认，不重复盘问
ff-spec目标明确，但缺产品/功能规格或规格过期主流程、行为、边界、错误路径、验收标准和追踪关系当前规格已覆盖本次目标和边界，可复用
ff-design关键视觉或交互方向需要比较、选择可评审设计候选、选择理由、状态与设计约束无相关视觉未知，或已有有效设计时跳过
ff-prove技术可行性、真实入口或环境能力有关键未知有界实验、结果、证据、限制与是否可继续的结论已有同等环境和版本的有效证据时复用；不把猜测当验证
ff-plan有规格，但需要实施拆解、重排或补票据可执行切片/票据、依赖、测试策略、证据要求与回滚考虑有效票据已覆盖当前规格且独立计划审核仍有效
ff-implement已获准且就绪的票据需要实现代码/配置/相关文档变更、测试结果、版本证据和检查点切片已实现且当前证据充分时不重复写；直接核对审核和交付缺口
ff-review计划准备实施，或切片/集成已可验证独立计划审核、目标与真实主流程审核、代码审核，各自结论与问题仅能复用范围、版本、依赖未变且适用的独立审核；不能以自评冒充独立审核
ff-deliver当前成果需要验收、PR、阶段交接短验收说明、证据索引、偏差/未验证项、人工接受状态与授权范围内 PR尚未达到交付门槛时可给明确受阻交接，不把受阻说成完成
ff-diagnose可复现故障、回归或 CI 失败的根因不明复现、证据、与风险相称的竞争假设及排除过程、根因与最小修复建议原因明确的低风险小修可内联；不为简单问题强造多个假设，不在此实现修复
ff-tdd已就绪且获准的实施切片内，有可测试业务行为逐条行为的真实 red → green 记录、最小实现与受影响回归证据文案、配置或不可自动验证变化可说明原因，使用适当检查；不强制每个函数都写测试
ff-handoff暂停、换模型、换会话或主动交接未完成工作出站检查点、版本/脏状态、已做/未做、运行中操作、证据与下一步无跨会话交接需要时可不运行；已有当前检查点可增量维护，不替代接收方 Intake

一个技能只处理自己的责任。ff-spec 不写实现计划代替规格；ff-plan 不包办实现；ff-implement 不把自测当独立审核；ff-deliver 不充当全能开发器。

新项目如何从想法走到交付

第一步 让目标足以作决定

使用 ff-grill 只追问会改变方案的重要问题：谁会用、解决什么问题、成功怎样判断、本轮不做什么、时间预算和权限有什么限制。明确决策人与尚待确认的假设。已有确认就引用，不重新问一遍。

示例提示词：请用 ff-grill 澄清一个团队预约工具的首个可交付切片。先确定目标用户、核心场景、成功条件和非目标；只问会改变实现方向的问题，先不要写代码。

第二步 把目标写成可验收规格

使用 ff-spec 记录用户行为、真实主流程、状态变化、边界和错误路径，以及可观察的验收标准。规格回答“做什么、为什么、怎样算满足”。记录需求标识，方便追踪到票据、测试、审核证据。

示例提示词：请用 ff-spec 把已确认的预约目标形成规格。覆盖创建预约、冲突处理、取消、权限边界和失败提示，并给出可操作的验收标准。复用现有项目文档路径。

有重要视觉未知时使用 ff-design；有技术或真实环境未知时使用 ff-prove。它们的结论要反馈到规格；必要时回到 ff-grill 重新决定取舍。它们是有条件的支线，不是每个项目必须经过的仪式。

示例提示词：请用 ff-design 比较两个移动端预约交互方向，说明各自取舍，等我选定后把选择反馈到规格。

示例提示词：请用 ff-prove 验证现有日历接口是否支持重复预约和冲突检测。限定实验范围和停止条件，保留真实请求结果，区分已验证、受阻与未知，不把原型直接当正式实现。

第三步 从规格到票据 再独立审核计划

ff-plan 把规格拆成能独立验证的最小切片。每张票据应能找到目标/规格依据、实施范围与依赖、验收标准、测试与证据要求、风险、完成条件和必要的回滚处理。跨切片的集成路径也要明确。

示例提示词：请用 ff-plan 根据当前规格拆分实施票据，按最小可验收主流程排序。为每片列出依赖、验证命令或手工步骤、证据位置与阻塞条件，不开始实现。

随后用独立评审者执行 ff-review 的 plan 审核。评审者检查计划是否覆盖目标、主流程和风险，是否有真实可用的验证入口，是否过大、遗漏依赖或把假设写成事实。审核失败回到计划；发现需求矛盾回到规格；修订后对受影响范围复审。

示例提示词：请安排独立评审者用 ff-review 审核这份计划，review_kind=plan。重点检查需求覆盖、票据可执行性、真实入口、验收可操作性和依赖风险。不要写实现代码。

这里的 review_kind 是责任选择语义，并非已验证的命令行参数。计划审核发生在实施前，不能等到项目末尾才补。

第四步 按获准切片实现与验证

ff-implement 先核对计划审核、切片 readiness、当前权限和工作区，再执行实现、相关测试与文档维护。只推进已就绪且获准的部分；缺口只阻塞依赖它的部分。保持切片小而完整，避免一次改动跨越大量无关需求。

示例提示词：请用 ff-implement 实施已审查的预约创建切片。仅在已确认范围内修改，保留现有未提交改动，运行对应测试，把证据绑定当前版本。发现规格缺口先标出影响并回到相应责任。

第五步 独立检查真实主流程和代码

对相关切片与集成执行 ff-review 的 goal-mainflow 与 code 两类独立审核。主流程审核从真实用户入口走通用户目标，识别占位页面、mock 数据、未接入按钮和不可达结果。代码审核检查实现风险、可维护性、相关回归与测试可信度。实施者自测有价值，但不是独立审核。

示例提示词：请由独立评审者用 ff-review 检查当前版本，分别给出 goal-mainflow 与 code 结论。主流程从真实入口验证预约创建与冲突处理；代码审核检查状态一致性、失败路径和回归风险。列出证据与未运行项。

审核发现实现缺陷，回 ff-implement 修复、复验，再复审；发现目标或规格偏移，回 ff-spec，分析哪些票据与证据失效。不用不相关的全量重跑代替有依据的影响分析。

第六步 验收与交付

ff-deliver 先区分验证、接受、规格合入和归档状态，再整理当前版本、访问入口、操作步骤、期望结果、证据、偏差与未验证项，并单独记录人工接受。没有用户反馈时写“待接受”；技术通过不代表用户已经接受。交付可分阶段，不必把未完成部分藏起来。

示例提示词：请用 ff-deliver 整理这一切片的短验收说明和 PR 草稿。列出版本、真实入口、验证结果、独立审核、风险、未验证项和人工接受状态；只有已有仓库授权覆盖时才执行提交 PR。

只有仓库采用 PR 工作流且已有授权时才准备或提交 PR；不采用 PR 工作流的项目可以交付文件、证据包与交接说明。PR 是代码审查与交付载体，不是规格文档，也不是自动合并、部署或发布的授权。若仓库允许未验收草稿 PR，可如实标明草稿与待验收状态；不得把它称为最终验收完成。

旧项目或半成品项目怎么接手

先只读盘点

ff-intake 先核对当前有效规格、活跃变更及必要的归档记录，再读取现有目标与确认、票据/计划、代码、测试结果、分支/提交、未提交与未跟踪文件，以及检查点和仍在执行的操作。报告“已知什么、缺什么、哪些材料失效、下一步该承担哪项责任”。Intake 本身不写文件、不重置工作区、不替别人改计划。

示例提示词：请先用 ff-intake 只读接手这个半成品。对账目标、规格、任务、代码、测试、分支和脏工作区，区分有效、过期、缺失、未知。指出下一步应进入哪个技能，先不要修改文件或重复运行可能有写入副作用的操作。

四种明确分流

  1. 目标缺失或不清楚：进入 ff-grill；目标清楚后核对规格，再补必要的计划与审核。
  2. 目标清楚，但规格缺失或过期：进入 ff-spec；有设计或技术未知再选 ff-design / ff-prove，结论回写规格。
  3. 规格有效，但票据缺失或过期：进入 ff-plan，随后执行独立 plan 审核。
  4. 规格与票据都有效：复用现有产物。核对独立计划审核、实施条件和授权；通过后进入 ff-implement，不能因“文件都在”直接开工。

任何分支遇到 unknown 都先核实，不能把未知等同于 valid。若实现已经完成，则按实际缺口进入验证、独立审核或 ff-deliver，不为走流程重复实现。

示例提示词：若现有规格和票据仍有效，请不要重写它们；只核对受影响的审核、测试证据和授权。选择可继续的最小切片；不满足就绪条件就报告具体缺口。

暂停与恢复

暂停或换模型/会话时，用 ff-handoff 准备出站检查点。Mode 0 仅在当前回复交接，不落盘；仅在模式 1/2 且已有对应记录授权时，才在项目约定的位置保存，至少包含当前版本与脏状态、已完成和部分完成产物、运行中操作、已知失败和阻塞、有效证据、下一步以及权限边界。敏感凭证不进入检查点。

恢复先用 ff-intake 对账实际状态。确认旧命令是否结束、外部操作是否产生结果，再决定是否续跑，避免重复写入或重复提交。重新检查环境、权限、依赖与证据有效性。检查点是可恢复信息，不承诺自动唤醒、进程持续存活或宿主跨会话状态保留。

三个执行方法如何嵌入主流程

这三个方法补足执行细节，不新增三个必经阶段。Diagnose 是故障支线，TDD 是 Implement 内的实施方法，Handoff 是任意阶段的出站检查点。进入实际修复或 TDD 实施前仍须核对有效规格、票据、独立计划审核、环境及授权；只读诊断和准备交接不要求先补齐全部实施产物。方法名不能绕过相应门槛。

ff-diagnose 先定位 再由 Implement 修复

先明确实际行为与期望行为、影响范围、复现步骤、版本和环境。优先建立最小可复现；无法复现时保留未知和所需证据。复现命令须覆盖真实故障调用链并断言用户实际症状，至少实际运行一次；没有工具或无法复现时标为 NOT_REPRODUCED / UNKNOWN，不能宣称原因已证实。性能问题先保存可比基线和条件，再测量定位。根据问题复杂度列出可区分的解释，用最小实验排除或证实，记录观察结果与根因的联系。简单拼写或边界错误可以只有一条清晰证据链；复杂间歇性故障才需要多组竞争假设，不固定要求 3–5 个。

定位输出交给 ff-implement：根因、影响、最小修复建议、回归测试与剩余未知。诊断不顺便重构或直接修生产；修复后仍做对应验证与 ff-review。若问题实际是需求不清，回到 Spec；若是新技术可行性未知，考虑 Prove。Diagnose 解释已经出现的故障，Prove 验证尚未成立的技术能力。

示例提示词：请用 ff-diagnose 定位预约跨时区后时间偏移。先只读检查并复现，记录实际与期望、版本和证据，按复杂度检验假设，给出最小修复与回归建议。不要把定位授权当成修复授权。

ff-tdd 在 Implement 内一次验证一个行为

从已认可票据和验收标准选择一个可观察业务行为。先写最小测试并实际运行，确认它因目标行为缺失而失败（red），不是因为环境、导入或测试写错。只实现让这一条通过的最小代码并实际运行（green）；green 后运行必要的受影响回归，再选择下一行为；不把重构作为每轮必经步骤。重构先交 ff-review 提出只读审查建议并完成范围门控，再由 ff-implement 在已获准范围内实施和复验；较大的接口、职责或结构变化返回 Plan，必要时先更新 Spec。完成这条后再进入下一条，避免先批量生成全部测试再批量实现，也不把未运行的测试称为 red 或 green。

测试期望必须来自规格、独立人工算例或已知正确固定值，不能复制被测算法来生成“预期”。复杂跨调用者故障须覆盖实际触发链，不能用浅层替身的绿灯代替。测试优先保护用户可见行为、业务规则和稳定的模块边界。只在外部服务、网络、时钟等必要边界使用替身，明确替身不能证明真实集成。单元测试不替代真实主流程、集成、独立审核或用户接受。不要为了覆盖率强迫每个函数都有独立测试，不把私有实现细节当稳定契约。纯文案、文档或某些配置修改可记录不适用理由和替代验证；必须测试的风险不能用 N/A 跳过。

示例提示词：在已获准且计划审核有效的创建预约切片内，请用 ff-tdd 先做“冲突时拒绝重复预约”这一行为。实际运行失败测试，再做最小实现、运行通过；如需重构，先交 Review 审查并核对范围门控，更大变化返回 Plan。记录命令、结果、版本和未验证的真实集成边界。

ff-handoff 写出站检查点 Intake 核验入站状态

Handoff 把当前工作整理给下一位执行者：目标与确认、当前分支/提交和脏状态、变更文件与部分产物、已运行验证、失败/阻塞、仍运行或结果不明的操作、下一条可执行步骤、授权边界、恢复前要核实的事项。内容应足以继续，不堆整段聊天记录，不保存凭证。

Mode 0 仅在当前回复给出检查点，不保存持久化记录；一般开发写入授权不改变这一记录模式。仅在模式 1/2 且已有对应记录授权时，优先写到项目已有的交接或检查点位置；没有约定时在对应记录授权内选用项目本地文档位置。外部方法中出现的临时目录仅是示例，不把临时文件当唯一持久交接载体。未获写入权限时在回复给出检查点草稿并说明未落盘。只有写入成功且验证路径后才声称已保存；跨环境要核实接收者可访问，否则标为待传输。交接不自动启动新会话、代理、后台任务或重跑命令，不承诺进程跨会话存活或自动恢复。检查点引用真实授权，本身不能授予或扩大权限。

接收方必须用 ff-intake 只读核对实际文件、分支、脏状态、进程与外部操作结果，再判定检查点有效性。不要照抄检查点就继续，更不要重复执行结果未知的写入操作。Handoff 用于工作中断/转交；Deliver 汇总当前成果供验收或正式交付，两者不能互相替代。

示例提示词：请用 ff-handoff 为换会话准备检查点。Mode 0 仅在当前回复交接，不落盘；仅在模式 1/2 且已有对应记录授权时复用项目既有交接位置。记录当前版本、已做/未做、运行中操作、证据、下一步和权限边界。下一会话先用 ff-intake 核对实际状态后再继续，不把这次交接标为最终交付。

小修怎么保持轻量

范围明确、风险低的小修可以使用内联规格与内联票据，不强制制造一整套新文档。例如：“修正移动端按钮被遮挡”可以用简短记录说明受影响入口、期望行为、非目标、改动边界、回归步骤和完成条件。

可跳过没有实际未知的 Grill、Design、Prove；已有有效内容直接复用。规格与计划的职责仍保留，独立计划审核可以很短，相关主流程与代码审核也按风险缩放。轻量不代表省掉验收、权限、验证、独立性或变更影响记录。先保护已有修改，再实施。

示例提示词：这是一个明确的小修。请用内联规格和票据记录目标、范围、验收及验证，做与风险相称的独立计划审核，再实施和独立复核。不要扩展成无关重构。

变更时哪些内容失效

需求变更先确认其目标、范围、预算与权限是否仍在授权内。对获准变更分析受影响的规格条目、票据、测试、审核、证据和人工接受；将受影响内容标为 stale 或待复验，保留未受影响的有效证据。不要把旧版本的通过或用户接受自动继承给新版本。

例如把“单人预约”改成“多人共同预约”，可能影响冲突规则、权限、数据模型、主流程、测试与用户验收；纯文案修正可能只影响截图和相关验收，不一定使全部后端测试失效。范围扩大或涉及新权限时重新取得必要授权。

材料有效性统一用 valid / stale / missing / unknown。测试和验证结果统一用 PASS / FAIL / NOT_RUN / BLOCKED / N/A；N/A 要说明为何不适用。未测量的 CRAP 指标记为 NOT_MEASURED，不用猜测填值。不运行或受阻的检查不能算通过。

产物如何放置和追踪

优先复用项目已有的文档、规格、任务、测试和审核位置，不强制所有仓库改用同一组文件名。建议保留从目标 → 规格条目 → 票据 → 实现版本 → 测试 → 独立审核 → 人工接受 → PR/交接的可追踪关系。

  • Intake：只读报告放在当前回复或宿主已有的只读报告出口；不因接手擅自落盘改项目。
  • 目标与规格：区分已确认、待确认和假设，保存本次范围与非目标。
  • 设计/实验：保留选项、结论、适用环境、限制以及反馈到的规格条目。
  • 票据：每片有范围、依赖、验收、验证和状态，不用 PR 描述倒推需求。
  • 诊断：记录复现、证据、根因、影响与修复建议，保留尚未证实的假设。
  • TDD：按行为保存实际 red/green 与受影响回归记录与验证边界。
  • Handoff：准备出站检查点；Mode 0 仅在当前回复交接；模式 1/2 且已有对应记录授权时才复用项目位置落盘。接收时由 Intake 对账，不继承未核验状态。
  • 实现与验证：记录版本、命令/步骤、实际结果、证据位置及未验证项。
  • 独立审核：区分 plan、goal-mainflow、code，记录评审者独立性、覆盖范围和复审状态。
  • 交付：单列技术完成、用户接受、PR 状态和发布权限，方便接手而不混淆。

包内 ROUTING.md 是轻量路由说明；共享状态契约位于 skills/ff-intake/references/state-contract.md。它们帮助选择下一责任，不强制固定顺序，也不提供未经验证的宿主调度能力。

授权边界和完成判断

实施就绪只说明材料、依赖和验证条件足够，不扩大授权。已有工作计划范围内可以按当前授予权限执行开发、测试、相关文档和计划维护、工作分支提交；仍须遵守仓库规则和平台确认要求。主分支合并、发布部署、额外付费、扩大持久访问及安全敏感设置变更不因技能流程自动获得许可。

每个阶段的状态要可核查：计划通过不等于代码通过；代码通过不等于真实主流程通过；技术完成不等于人工接受；PR 创建不等于合并或上线。阻塞时报告具体缺口、影响范围和下一步，不把未知变成承诺。

  • FF-中文使用手册.md：可编辑正文。
  • FF-离线图文手册.html：内嵌三张 SVG、样式与目录筛选脚本，直接在浏览器打开；无需联网或额外字体下载。
  • diagrams/new-project-workflow.svg 与 .png：新项目流程矢量版与图片版。
  • diagrams/existing-project-workflow.svg 与 .png：已有项目接手流程矢量版与图片版。

  • 三个同名 .drawio：在兼容 draw.io 的编辑器中打开，可编辑节点、文字、连接线、标题、分支标签和页脚说明。
