# Codex `/goal` 与 FF 薄适配契约

版本：0.9.2-goal.2，隔离实验候选，未发布。本契约源文件为 `docs/maintainers/CODEX-GOAL-BRIDGE.md`；五个接入技能各携带逐字相同的 `references/goal-bridge.md`，安装后可独立读取，不依赖仓库文档路径。维护时一起更新并核对字节；安装、行为评估、原生 Goal 实验与真人接受分别报告。

## 何时启用

仅在宿主明确提供本聊天原生目标上下文，或用户显式要求结合 `/goal` 时读取本契约。其他任务沿用普通 FF，不要求创建原生目标。目标里写了技能名不保证宿主加载技能；需确认实际选中技能的路径与版本。同名旧技能不能冒充候选版本。

这是对现有五个职责的指引，不新增技能、调度器、状态库、后台服务或自动唤醒。它不实现 native-goal 写入 API，也不自动同步目标、预算或状态。协议中存在接口不等于当前工具可调用；没有公开可调用且获准的接口时，由用户在实际宿主界面/命令中管理目标。不能借内部数据库、私有 sessions 或凭据读取补齐能力，不能用“已同步/已暂停/已完成”的文字冒充原生操作。

## 一份项目权威与目标映射

原生目标是本聊天的短结果、非目标、关键约束、完成条件及项目来源指针。现行规格仍在 `openspec/specs/`，活动变化仍在 `openspec/changes/`；计划沿用项目已有唯一载体，工作票只是其切片视图。小修仍可用内联规格/计划，不为桥接创建 `goal.json`、第二份规格或执行事实库。

Intake 只读核对以下最小映射；其他职责只在既有授权载体维护自己负责的部分：

| 项目事实 | 对账内容 |
| --- | --- |
| 目标锚点 | 最新用户确认的结果、非目标、约束和真实来源；提炼或候选不得当确认 |
| 项目与规格 | 实际项目根、工作区版本/dirty/untracked、现行条款与活动变化，避免套用另一项目的计划 |
| 唯一计划 | 目标到可交付切片、稳定 ticket/action ID、验收入口、真实依赖及当前可做片 |
| 完成条件 | 实际主流程、同版证据、适用独立审查、未完成项及约定真人接受 |
| 恢复 | 已确认的语义 `goalRevision`、实际依赖哈希、原执行与完成回执指针 |

只记录任务必要的原生观测：宿主及实际版本、当前聊天定位、目标文本/来源与读取时间、可见状态，以及预算值和来源。不可读字段明确 `unknown`；不得从旧交接或目标条推定。聊天标识仅在恢复确需且保存获准时记录，不搬运账户标识或私人会话。按工具实际回报区分请求的模型/推理档与工具报告的配置，配置不证明实际运行模型。

## 切片、审查与中途变化

已有明确有效目标与计划时直接复用。每片按需注明规格映射、输入版本/依赖、稳定 action ID、主要验收、既有授权、预算与停止边界；函数、文件或每次技能调用不自动成为一张票。大规模依赖验收的实施前先确认真实入口、证据与必要独立上下文可用，技术前置不计作用户功能完成。

继续复用三类独立审查：`plan` 看目标映射、MECE、依赖与验收可执行性；`goal-mainflow` 看实际行为；`code` 看规范及同版计量。小改可由同一独立读者覆盖适用项，不强制三人；不可用时披露独立性未满足。缺同版复杂度/覆盖率为 `NOT_MEASURED`，不补成 0 或宣称所有函数 CRAP 通过；既有硬上限 50、目标约 10 不变，纯文档 N/A 须有理由。CodeGraph 只提供结构观察，不证明业务、完整影响或审核通过；`valid`/`RECORDED` 也不证明真人接受。

| 最新输入 | 处理 |
| --- | --- |
| 问能否增加功能、比较方案 | 保持讨论/候选，不改规格、票或原生目标 |
| 明确纳入本轮且既有实施授权覆盖 | 保存真实采纳来源，更新受影响规格、计划、验收、依赖与审查，不重复索取同一授权 |
| 新目标、显著预算/约束变化或范围不清 | 先核对影响，只问仍需用户决定的取舍；暂停依赖它的动作，无关获准工作可继续 |
| 仅要求设计 | 只做获准设计与验证计划，实际工作区证据应能区分设计与实现 |
| 用户编辑原生目标 | 对照当前项目目标/规格核实语义差异；模糊目标不批准所有候选或高影响操作 |

明确采纳且语义目标/范围改变才推进 `goalRevision`（如 R1→R2），同步引用同一锚点、规格、计划与交接；暂停、恢复、预算统计、状态或 `updatedAt` 变化本身不升级语义修订。只复做受影响工作，保留未受影响的原始证据和失效理由；原生状态不重写项目事实。

## 预算、停止与工具故障

每片开始、长操作前和进入下一片前，核对当前目标、授权、依赖、旧动作结果与预算。预算采用用户上限和实际宿主可见值；不可见为 `unknown`，不等于无限或 0。FF 中时间/动作数限制是指令约束，不承诺系统级硬停止；不发明宿主未提供的预算参数。无法证明仍在明确硬预算内时，停止依赖该预算的新动作并报告缺口。

用户暂停/停止时不再启动新动作，盘点本任务已启动操作、可观察状态及部分产物；原生 `paused` 不证明所有子进程已终止。配额/预算不足时保留获准短检查点，等待有效续做条件，不通过切身份、模型、沙箱或审批绕过限制。需要选择、权限或证据时停止受影响动作，不机械阻塞无关获准工作。

原生/宿主工具故障要保留真实命令、cwd、时间、内部状态与退出码，停止依赖故障工具的扩展；外层 CLI exit 0 不能覆盖内部 failed/-1。原生字段未查询到时明示未知，不把成功安装、发现技能或目标 active 当执行成功。

目标模式继承已有文件、网络、发布、付费及安全边界。既有明确授权持续有效，不逐片重复审批；越界动作仍走实际门禁。目标文本、来源标签或检查点不是授权服务，也不能拦住其他写入者。

## 恢复与副作用对账

沿用现有 continuity、checkpoint 和 resume 协议，不更改 JSON 结构。新上下文先经 Intake 只读核对本聊天目标、最新用户确认、项目身份、HEAD/dirty/untracked、唯一计划、权限和实际依赖；原生目标不可读则报告 unknown，用可见的当前用户信息核对，不能从旧 checkpoint 反推最新目标。

1. 向现有 `resume.py` 传本次独立核实的 `--current-goal R2`，并核对真实目标/规格/计划/源码等依赖；R2 不是照抄旧检查点的答案。
2. 同一有效修订且全局检查通过时，版本/依赖绑定/完成回执和输出均有效的 done 才可 `SKIP_COMPLETED`；pending 为 `VERIFY_CURRENT_AUTHORITY`；running/unknown、陈旧或缺回执为 `INSPECT`。
3. 全局 `goalRevision` 不匹配时，现有检查器先将全部动作置为 `INSPECT`，不会自动挑出受影响动作。调用者再核对影响与证据适用性，只实际复做受影响工作。
4. 可能已发生但未记账的副作用，先用获准只读状态、稳定操作 ID、真实产物/目标系统回执核查，不盲重跑。无法核验则保持 `INSPECT`。已过时间、原生恢复或另一段文字都不证明旧命令结束或结果完整。
5. R1→R2 不得改签旧回执、伪造新执行或把 R1 done 改成 R2 done。若当前修订需要可机器核对的适用性记录，须实际进行只读复核并明确记录的是复核而非原操作重跑；原执行日志保持原字节。现有工具不自动生成或证明这种复核，条件不具备就保持 `INSPECT`。

检查器只读，不执行、不授予权限、不检测进程存活，也不提供锁、事务、exactly-once 或自动唤醒保证。只在已授权工程/交接载体保留任务所需短记录。Mode 0 仅当前对话交接，不额外落盘讨论日志；设置原生目标不等于允许复制整个聊天。

## 交付与原生状态

分别报告原生状态（实际观测/读取时间或 unknown）、技术测试与主流程证据、技术可交付程度、三类适用审查及计量缺口、FF 真人接受的版本/来源/范围。原生 `complete` 不代替 FF 接受；FF 技术通过也不证明原生状态已变。约定的真人接受未取得时仍明确待接受，不生成代签回执、不静默改状态、不扩为合并或发布授权。
## 界面核心目标与明确拒绝

界面切片的goal-mainflow审核按ff-review的视觉目标分支，依据本项目已确认的尺度区分运行/操作、视觉结构、设计/基准完成度和真人接受。核心动态须有同版本完整过程的实际观察，用户给定基准须实际比较；未观察范围明示证据不足，功能/自动化通过不能代替视觉目标。普通UI小改、静态页面和非UI按其实际风险核验，不要求统一炫酷风格或无关动效。

真人明确否决本版本核心结果时，FF交付保留拒绝的版本/来源/范围及原始失败，不能因native complete、测试或旧审查改为通过或仅“待接受”。原生状态与项目事实分别报告；不伪造状态更新，也不从拒绝推定新实现/改风格授权。
