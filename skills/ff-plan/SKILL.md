# FF-Plan 0.9.3-dual-host.1

把“已确认要做什么”变成可以交付的实施切片；计划本身不授予执行、向外部平台发布工作票或发布产品的权限。

1. 读取最新确认目标、范围、关键约束、需求来源和现有计划。引用规格，不抄第二份；设计验证只消费真实结论，未验证假设仍标未知。必要时查当前代码、术语与接口。
   涉及 UI 时引用已选可见目标的版本与短规则，把关键状态和目标平台检查放入相应业务切片。视觉方向尚待选择时只规划获准探索和独立业务部分，不把整站实现标成可开始；已有明确设计不强制重走 Design。若连续转场是核心，把关键边界样片安排在其依赖的整段扩展之前，消费真实结论而非仅静态选图；普通业务不增设该步骤。
2. 在依赖验收能力的大规模实施之前，按 [切片与依赖](references/slicing.md) 做最小验收可行性预检；低风险小改只核对相关入口与检查。半成品或恢复任务先对账已有状态，只拆剩余切片。按 [切片与依赖](references/slicing.md) 拆解。每片要说明完整行为、映射到同一需求锚点的原话/确认需求、可观察验收、真实阻塞和排除项；不是数据库/API/UI分别做完才首次可用。粒度让一次交接能完成可验证闭环，不以固定票数、工时或上下文长度保证成功。
3. 将计划交 ff-review 的 plan 职责，实现前及需求变更后由独立子代理/新上下文只读做计划审核（不可用时披露独立性未满足）：按 [切片与依赖](references/slicing.md) 的 MECE 检查任务边界不重不漏、目标映射、真实依赖和验收可执行性；与后续主流程/核心需求审核、代码规范审核分别给结论。核对已确认需求都有落点；多片共同承担的约束有明确整体验证位置。明确本轮不做和依赖仍未知的内容，不能把“后面再说”当已覆盖。先安排价值高或风险高且前置具备的路径，用户有指定顺序则优先遵守。
4. 给人看简洁的“每片交付什么、如何验收、依赖什么、下一片是什么”。已有确认计划范围内的细分/状态维护直接做；新增目标、预算、关键约束或重大粒度取舍才确认。没有授权实施时停在计划，不让 ready 标签暗示获准开工。
5. 用户新确认或实现证据改变计划时，走最短影响链：确认采纳来源 → 受影响目标、调用者与已完/未完切片 → 失效证据及用户接受范围 → 最小复验 → 可保持不变的部分。只重排受影响部分，保留旧→新理由与当前状态；相关验收/依赖一起更新。已完成内容若受影响需复验，不悄悄继续用旧绿灯，也不无故撤销无关结果。复用唯一已有计划载体，不复制成四阶段事实库。

默认在对话或已授权任务文件中写计划。小修可一句目标加检查点，复杂切片才分票；Mode 0 不新增讨论记录，工程计划文件按自身授权管理。外部发布票、分支操作及多代理执行遵循其授权，列出依赖不等于获准并行。

ff-grill 可用于缺失的重要目标选择，ff-design 用于重要视觉方向待选，ff-prove 只用于会改变拆分的真实交互/技术未知，ff-implement 执行获准计划；它们都不是本技能运行前置依赖。[来源与许可](NOTICE.md)。

## OpenSpec 与 FF 有效性

遵循 [规格生命周期契约](references/spec-lifecycle.md)。所有 FF 子命令均通过项目本地 `node tools/openspec/ff-spec.mjs` 运行，工作目录为目标项目根；工具不在此相对位置时使用其真实路径，不回退到全局官方 CLI。仅允许 `init --tools none`，不刷新官方工具集成，`update` 拒绝；包名 `@forgeflow/ff-spec`、用户配置/数据命名空间 `ff-spec` 与官方入口分开，项目 `openspec/` 树仍兼容，这不是文件系统安全边界。现行规格只在 openspec/specs；活动 changes 保存差异和回执，Git 保存历史。按稳定 artifact ID、明确路径、排序内容指纹与依赖指纹判断有效性；review 必须绑定目标版本/内容及依赖。文件存在、任务勾选或旧审核均不自动代表 ready。status / instructions apply / validate / archive 共用 FF evaluator；apply 是实施指导，archive 正常路径同步规格并保存历史。不得继续写旧 spec-state.json，不自动导入旧接受或伪造 pass；取消/拒绝只能走显式 disposition+原因+决议引用的关闭路径，保留失败/未完成记录且不合入规格、不制造 pass。三类独立审核、真实主流程、CRAP ≤50（目标约10）、按需 Diagnose/TDD/Handoff 和既有权限边界保持不变。

## Codex 原生目标（条件启用）

宿主提供本聊天原生目标或用户显式要求结合 `/goal` 时，读取 [目标桥接契约](references/goal-bridge.md)。把已确认结果/完成判据映射到现行规格与唯一计划的纵向切片，按需补稳定 ticket/action ID、实际依赖、验收/审查入口、既有授权与预算停止边界。原生目标只放短结果和来源指针，不复制规格；讨论不入票，明确采纳的语义变化才推进目标修订并更新受影响部分。预算不可见为 unknown，计划不授予实施或原生状态写入权限；未触发时沿用普通 FF。

## 变更与恢复边界

明确获准加入需求后，对照同一目标锚点列受影响规格、任务、测试及依赖；缺一项说明理由，不能只追加任务而保持过期验收。纯讨论/澄清不自动入计划。已完成且证据仍有效的动作不重复拆票/重跑；当前目标/依赖变化只重开受影响工作，保留其他有效进度。
