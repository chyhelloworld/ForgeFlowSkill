# FF-Grill 0.9.6-architecture.1

从用户原话与现有证据提炼 Intent → Motivation → Goal → Problem → Decision → Evidence。保留用户意图，不用推测的“真正问题”替代它。

## 单一需求锚点

从可访问的多轮讨论、grill-me 与普通项目对话维护同一轻量锚点：提炼后的目的、总需求、约束、取舍、未知。展示摘要供用户判断是否符合；原话/出处仅按需追溯。已确认与 AI 假设分开，保留真实来源及历史缺口；其他阶段引用，不各抄一份。已有明确确认直接沿用，不逐轮重问。

让用户快速看懂“原来想要什么 / 现在改什么 / 实际做成什么”，给短差异与真实证据，不让用户读长文档或靠AI自评判断没偏。

## 开始与收敛

- 复用已确认背景、目标、范围与权限。只追问仍未知且会改变当前决策的事项，按风险选择深度，不跑固定阶段或凑问题/方案数量。
- 先读 [澄清与自审](references/clarify.md)：先查事实、按依赖分轮；每题的推荐和最终方案都先自审，再展示短理由、主要代价及不确定性。
- **最新确认优先**：用户改目标、呈现或范围时，区分“讨论可能性”“明确采纳”“仅授权原型/规格/实现”。确认只覆盖明确答复；未知项不撤回其余已知事实。把旧→新、来源与受影响的方案/验证同步到已有授权载体；不能悄悄保留过期验收标准，也不把新想法一律拒绝为范围膨胀。
- 术语确有歧义才核对现有词表与代码行为。词表只存定义；难逆转且有真实取舍、未来难理解的决定才考虑 ADR，并沿用记录授权。
- 已确认目标、关键约束和验证方式足够清楚时收敛；保留未知及重开触发条件。停止不等于确认，推荐不等于获准执行。

## 记录是可选项

已有授权工程载体先沿用；需要新增持久讨论记录且重要主题尚无记录选择时，简短问一次：0 不记录；1 关键决策摘要；2 完整讨论轨迹。选1/2时确认目的地或沿用已授权位置。未选择可继续讨论和查证，不自动保存；同主题不重复问。

启用记录或需解释模式时读 [记录模式](references/records.md)。Mode 0 在当前对话交接，不借其他技能创建持久讨论日志。Mode 2 保留可见关键问答、方案演变与确认来源，不输出私有思维链。

## 体验目标

涉及新界面或视觉改进时，把主要用户任务、目标平台、既有品牌/参考和已明确的审美偏好并入同一锚点，客观可用性与主观喜好分开。批评现有画面时核实版本/截图，不能推测用户已选新风格。缺少视觉方向可用 ff-design 形成关键页可见候选与真实选择；已有明确设计的小改不增加方案仪式。

## 后续动作

视觉/交互方向待选时可用已安装的 ff-design；实际交互或技术/架构存在影响方向的未知时，可用已安装的 ff-prove 做有界验证；已确认行为需成规格时可用 ff-spec；规格有效需拆票时可用 ff-plan；执行获准且计划有效时可用 ff-implement。它们不是前置依赖，不要求每次全部调用。交接只传当前目标及来源、获准范围、关键事实/未决项、下一步，不复制整份讨论。

本候选保留 v1.3 的核心语义并渐进拆分；[来源与许可](NOTICE.md)。不自带安装、T3集成、执行权限或行为测试通过保证。

## OpenSpec 与 FF 有效性

遵循 [规格生命周期契约](references/spec-lifecycle.md)。所有 FF 子命令均通过项目本地 `node tools/openspec/ff-spec.mjs` 运行，工作目录为目标项目根；工具不在此相对位置时使用其真实路径，不回退到全局官方 CLI。仅允许 `init --tools none`，不刷新官方工具集成，`update` 拒绝；包名 `@forgeflow/ff-spec`、用户配置/数据命名空间 `ff-spec` 与官方入口分开，项目 `openspec/` 树仍兼容，这不是文件系统安全边界。现行规格只在 openspec/specs；活动 changes 保存差异和回执，Git 保存历史。按稳定 artifact ID、明确路径、排序内容指纹与依赖指纹判断有效性；review 必须绑定目标版本/内容及依赖。文件存在、任务勾选或旧审核均不自动代表 ready。status / instructions apply / validate / archive 共用 FF evaluator；apply 是实施指导，archive 正常路径同步规格并保存历史。不得继续写旧 spec-state.json，不自动导入旧接受或伪造 pass；取消/拒绝只能走显式 disposition+原因+决议引用的关闭路径，保留失败/未完成记录且不合入规格、不制造 pass。三类独立审核、真实主流程、CRAP ≤50（目标约10）、按需 Diagnose/TDD/Handoff 和既有权限边界保持不变。

## 跨会话决策恢复（按需）

跨会话或复杂取舍容易丢失原始目标时，按 [决策索引契约](references/decision-index.md) 使用同一权威记录的轻索引。简单任务跳过；不新增技能、状态库或授权。沿用记录模式与保存授权，不自动落盘。

## 小范围证据补强

需求锚点按需区分：用户必须项、已知目的/预期变化、可观察结果证据、尚未确认的假设。保留按需追溯的来源指针；目的未知就写unknown，不替用户脑补或取消明确方案。明确小修改直接处理，不凑三方案、分数或风险配额。

## 技术方案路由
架构方案的目标、约束和取舍先由 Grill 澄清；会影响方案的技术假设未知时转 ff-prove 做最小实验，再由 ff-spec 将确认方案写入技术设计。ff-design 处理界面与视觉方向，不作为全部技术架构的入口。只补真实缺口，不要求三个职责串行。

## 需求驱动闭环（按当前任务使用）

在持续项目讨论、旧项目未知对齐或实质转向时，按契约提炼摘要并判断探索/决定；提示目标差异、复用与返工/迁移/维护风险及较小方案。用户已明确决定不重复审批。

转向影响说明输出前短检一次：是否既说明一次性返工/迁移，也说明哪些协作或状态会增加持续维护负担？没有明显增量可给理由，证据不足就保留未知；不靠新功能清单代替后果，不编成本数字，也不让已明确采纳的用户再批准一次。

具体来源、关联、转向、旧项目与设计协同遵循[需求闭环契约](references/intent-loop.md)；小改内联，同次任务已读且未变化时复用定位。
