# ff-review 0.9.5-review.1

review_kind=plan | goal-mainflow | code 是职责标签，不是 CLI 参数。普通任务先自检与确定性检查，阶段末默认由一名独立审核者一次读取最小证据包，分别给三类适用结论；必要专业视角才拆分。阶段是可独立验收的功能切片，不是每个小任务，也不能无限延至整个项目结束。

读取 [审核规则](references/reviews.md)，代码计量再读 [CRAP 数据与边界](references/crap.md)。拿原始用户目标/最新确认、现行规格/计划、冻结代码差异和原始证据；不先喂实现者“通过”结论或预期答案。独立子代理或真正新上下文只读核查；宿主不支持时标独立性未满足，角色扮演和作者自检不能冒充独立通过。

- plan：核对目标追溯、MECE、真实依赖、切片和可执行验收。普通切片并入阶段末综合审查；核心替换、主要用户路径、数据迁移、安全边界、验收口径变化必须实施前独立审方案；用户额外要求和既有门禁优先，风险不按行数/文件数判断。有效结论可复用，不将自检签成独立 pass。
- goal-mainflow：在相关切片完成和整合时，从核心目标检查真实主要业务流程、遗漏/越界及跨模块约束。涉及界面时读取[视觉目标审查](references/visual-review.md)，分别判断设计质量与运行证据；体验或动态是核心时必须实际查看同版画面、完整过程和用户基准，不能只抽查端点后给整体无阻断。局部改动只查受影响目标，非UI不套视觉流程。静态存在、单测或代码规范不能证明主旅程走通。
- code：可审差异形成后检查项目规范、职责、重复、耦合与可维护性。逐函数/方法 CRAP 硬上限 ≤50，优化目标约10或更低；只用同版本真实 CC 与覆盖率计算，缺数据 NOT_MEASURED，不能捏造或拿估计值充通过。纯文案无逻辑变化可说明 N/A，不扩大成无关全仓重构或刷测试。

每类分别给结论、版本、直接/间接证据、缺口与下一步；PASS/FAIL/待验证/有理由的 N/A 分开。发现交实现者或相应规格/计划职责修复，仅独立复核已发现问题及受影响依赖；无关非阻断建议进待办。新关键缺陷继续阻断，不用轮次/token上限强制放行。关键未知不能判通过，独立的无关工作可继续。审核不批准合并或代签用户接受。

补充专项核查：Diagnose 的症状/根因/因果证据、TDD 的独立期望/真实调用链/实际 red→green 不能被模拟替代。必要局部重构可在已获准切片内自检并纳入阶段末审核；核心替换或重大接口/职责、验收变化先回 Plan 独立审方案，额外门禁仍遵守；本职责只读。

## OpenSpec 与 FF 有效性

遵循 [规格生命周期契约](references/spec-lifecycle.md)。所有 FF 子命令均通过项目本地 `node tools/openspec/ff-spec.mjs` 运行，工作目录为目标项目根；工具不在此相对位置时使用其真实路径，不回退到全局官方 CLI。仅允许 `init --tools none`，不刷新官方工具集成，`update` 拒绝；包名 `@forgeflow/ff-spec`、用户配置/数据命名空间 `ff-spec` 与官方入口分开，项目 `openspec/` 树仍兼容，这不是文件系统安全边界。现行规格只在 openspec/specs；活动 changes 保存差异和回执，Git 保存历史。按稳定 artifact ID、明确路径、排序内容指纹与依赖指纹判断有效性；review 必须绑定目标版本/内容及依赖。文件存在、任务勾选或旧审核均不自动代表 ready。status / instructions apply / validate / archive 共用 FF evaluator；apply 是实施指导，archive 正常路径同步规格并保存历史。不得继续写旧 spec-state.json，不自动导入旧接受或伪造 pass；取消/拒绝只能走显式 disposition+原因+决议引用的关闭路径，保留失败/未完成记录且不合入规格、不制造 pass。三类独立审核、真实主流程、CRAP ≤50（目标约10）、按需 Diagnose/TDD/Handoff 和既有权限边界保持不变。

## 小范围证据补强

审查摘要保持短而可复核：一句目标/原因，关键变化与风险，绑定版本的证据，未完成项与下一步。需要时才给小图，不强制固定条数或AI总分。需求必须项、目的结果和推测分别审，缺真人接受不能称最终完成。可选运行本skill的scripts/health.py生成只读证据健康摘要；RECORDED仅说明记录可核验，不是语义审核或用户验收。阅读[健康摘要协议](references/health.md)。


有界旅程复核：核心目标/主要流程审查对照完整路径的预期与同版实测，指出缺步骤、状态断裂及只有截图没有真实操作的结论缺口。CodeGraph 仅为结构线索；不得代替业务结果、视觉判断或人类接受。

## 固定审阅版本与失败分流
v2 审核前生成 `receipt snapshot CHANGE FILE`，审核者核对快照的适用规则、每个文件的实际字节摘要和依赖输入；HEAD 不能代表 dirty workspace。审核报告记录 snapshotHash、逐产物结论和未验证范围，使用 `receipt template` 生成的 not-reviewed 模板可避免手拼字段。结束前运行 `receipt check CHANGE SNAPSHOT`；变更后只能复核受影响范围，不能把旧结论绑定到最新指纹。生产者用 `receipt record` 录入已完成报告，工具不默认声明 pass，证据替换会失效。内容绑定不认证审核者身份。
FAIL 按原因处理：需求冲突回 Grill/澄清；技术假设未知转 Prove；计划漏项回 Plan；审核意见冲突先裁决。不能机械按次数切换、把不同 change 的失败合并计数或默认全测；失败测试只是已知依赖的下界。
