# 分轴审查与版本交接

## 有效比较点

审查变更前核实基线可解析，说明是直接差异还是 merge-base 差异；选与任务相符的方式，不机械用 HEAD~1。锁定目标 commit 或包含未提交/未跟踪内容的可复核快照。展示实际文件清单与非空 diff；空 diff 不能称变更已审。先排查比较点或遗漏工作区，确无变更就如实报告。未跟踪文件须纳入范围而不是只靠 git diff。

## 三类审核分别成立

按风险选择深度，可并行但不互相代替；复用同一任务记录与证据，不要求三份长报告、固定三名代理或新增流程平台。小改仍分别判断适用范围，短结论足够；确实不适用时写明理由，不把未审核伪装成通过。

1. **主要流程与核心需求审核**：从唯一需求锚点、用户原话和最新确认出发，检查遗漏、越界、全局偏离及跨输出约束；实际走通承诺的主旅程，在纵向切片完成时和最终整合时验证。依据实际入口/操作/结果与版本，不能用 lint、单测、代码规范或漂亮分屏证明整段体验。
2. **代码规范审核**：开发形成可审差异后，检查仓库规范、复杂度、重复、职责、耦合及可维护性；按变更风险观察有问题的边界，区分硬规范与建议，不用个人风格强加重构。CRAP 审核采用用户指定的逐函数/方法硬上限≤50、约10或更低优化目标，按 [CRAP 数据与边界](crap.md) 核对本次适用范围与同版本数据；缺可信计量标 NOT_MEASURED，不能当指标通过。仅文案等不涉及相关逻辑变更时可说明计量不适用，不强造全仓计量任务；仍继续有证据的规范审查。代码通过不说明需求正确。
3. **计划审核**：实现前，以及需求/关键依赖变化后检查目标映射、MECE 不重不漏、真实依赖、切片与验收可执行。若已有审核则核对版本及本次变化是否影响它，只重开受影响部分；必要时用 ff-plan 或直接检查当前计划，不要求安装其他技能。MECE 不等于按文件拆分或禁止共享依赖；清楚的责任/边界不能掩盖漏目标、假依赖或缺整合验收。

每类分别给：结论（通过/未通过/待验证/有理由的不适用）、对应版本和证据、重要缺口/下一步。可在短回复中三行完成，不强制新模板。代码测量中的 NOT_MEASURED 是具体指标状态，不自动让整类代码审核通过或失败。三类不能平均分或抵消；主流程失败时不能因另两类通过宣布整体完成。未知不等于失败或通过，要限定可得结论。仅有路径名/依赖检查时可确认这些局部事实，但关键目标映射或可执行验收仍缺证据，就将整类计划审核标为待验证，不能一边待核关键项一边宣布该类通过。

按影响提供复现/原始输出与建议；无依据怀疑标待验证。默认交给独立子代理或真正独立的新上下文审核，不能把实现者自检当成独立通过。小变更可由一位独立审核者覆盖三类合理适用项，短答即可；复杂变更按风险拆分或并行，不强制固定三人。审核者只读，发现交回实现者修复，再由独立审核者复核受影响结论。无法创建独立审核上下文时，可以继续明确标注的自检，但必须说明“独立性未满足”，不能由主模型扮演几个角色冒充。沿用当前宿主支持的机制，不依赖某个特定工具。

独立评审先拿原始需求/目标、最新确认变化、现行计划、冻结代码或可复核diff及真实原始证据，明确三类审核范围；不先喂实现者的“已通过”结论或预期答案。评审后再核对作者解释。修复后在新版本复核相关发现和回归，不抹去原始失败；静态检查、复跑结果与引用他人日志分别标识。
