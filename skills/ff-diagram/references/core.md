# 图法：先答问题，再画关系（按需读取）

仅当当前授权交付需要创建/修改/审查架构图、DFD、E-R、UML或流程图时使用；纯文字、小改、无图任务不加载后续文件。它是现有职责里的表达与检查方法，不新增阶段、审批、固定图集或必需平台；推荐架构推导/评估仍不等于用户选择。原有只读审查不会因此获准改图。

## 选择最小视图

先复用输入，简述图要回答的问题、读者、范围/边界、当前还是拟议、粒度和记法。用途不明且会改变模型才澄清；否则明示合理假设继续，不开全套问卷。

| 当前问题 | 只加载对应参考 |
| --- | --- |
| 系统边界、逻辑组件、源码依赖、运行/部署关系 | [架构视图](architecture.md) |
| 数据从哪来、如何变换、去哪存/输出；实体关系与约束 | [DFD与E-R](data.md) |
| 对象结构、交互时序、活动/状态、用例、部署或其他UML；普通流程图 | [UML与流程](uml.md) |

不为齐全一次画完所有图，也不把全部参考自动读入。同一系统可有多视图；跨图保持对象ID/名称及事实一致，冲突明确指出，不用一个含混箭头混装数据、控制、调用、源码依赖和部署。

## 从模型到图

1. 先抽取最少模型：对象/参与者、边界、关系方向与类型、条件/基数、状态归属、输入输出和重要失败。关联原始需求/资料位置；区分用户已确认、已观察事实、AI推断/候选、unknown。没有来源的业务规则不因画入图变成承诺；原资料冲突先标明。
2. 主路径走读：谁发起→哪个对象/模块执行哪项操作/方法/契约（必要输入）→结果/失败由谁接收→谁决定下一动作和状态。现成API要核实，未实现操作标拟议；无需为画图硬造类、接口或包装。结构图不必塞进全部步骤，必要时辅以短时序/关系表；不要用图框数量代替路径完整性。
3. 按所选记法审语义，再排版。标签尽量具体（“提交订单”而非“处理”，“订单数据”而非“信息”）；保留原业务名称。关系方向/类型/边界由含义决定，不能为了美观改成错误方向。
4. 选择现有可用的可编辑格式，例如 .drawio、.puml、.mmd、结构化模型或原生矢量文档；不强推平台。保存源文件，记录导出与源的版本/hash关联。纯PNG不是可编辑模型；若用户只要片段，可交源文本并说明未导出。工具不支持所需符号时换格式或显式注明简化、附文字语义，不冒充严格符合标准。

## 布局与交付核对

布局是实践建议而非所有图共同的ISO规范：同图主要阅读方向一致、同类对齐、边界留白、层级可辨；减少交叉和回折，边标签贴近对应线且不压节点；颜色可辅助，不单靠颜色传达区别。图太挤按问题拆视图，不以缩到无法阅读的字体解决。页幅/字号按交付媒介选择，不硬定节点数或层数。

在当前可用渲染器中导出，并查看实际导出图：文字完整、箭头端点/线型可辨、无遮挡裁切、边界/图例清楚，按最终尺寸仍可读。修改后重渲染相关视图再检查。只读审查不修改原图，可在获准临时位置用现有本地工具渲染副本并实际查看，也可复核同版已有渲染证据；保留原件字节不变。没有相应执行授权/工具时说明限制，不擅自安装或运行外部服务。

分别报告：①模型语义走读的发现/未知；②工具语法/渲染是否成功（工具及版本、源与输出位置）；③实际视觉检查的发现/未检查；④用户业务规则/取舍是否确认。**语法能编译、XML可解析或图能渲染，不是语义正确证明；未渲染或未实际查看不能说视觉通过。** 无渲染器时交源和未验证项，不伪造截图；小图可简短内联结果，不另建仪式/状态库。按原任务停止条件交付，不以此强制新独立审查或用户签字。
