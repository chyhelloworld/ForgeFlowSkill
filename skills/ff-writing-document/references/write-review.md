# 正文编排与读者走读

## 成文

遵守已确认目录，按读者已有知识引入概念。每节解决一个读者问题；章节标题应让读者知道能找到什么，而不是只表达作者写作过程。

- 需求/方案可用“谁，通过什么入口，做什么，得到什么”描述功能与流程。技术文档可以精确到对象/接口；业务文档先解释用途，不隐藏必要技术边界。
- 报价/概算写明工作范围、数量或人日、单价来源、计费口径、估计条件和未含项。内部成本与对外售价分开；未给利润不得编利润。检查总额和明细一致。
- 报告先呈现问题、当前进度、实际结果与结论，区分完成、失败、未测。按读者用途保留必要过程，不用测试数量替代真实结果。
- 内部纪要保留必要讨论、分歧、决定及待办；不能把清除对外内部口吻的规则机械应用成删除纪要讨论记录。只记录材料确有的立场：未记录一致决议，不等于已证实意见不一致；有人暂不同意，也不等于另有人已赞成。

不用“按用户本轮选择”“不另设一套确认记录”等助手协作状态解释客户方案。可改为实际口径，如“工作量为概算，金额按确认的人日单价计算”。同时保留读者需要知道的条件，如“采购前用拟选标签与客户手机验证，形成支持设备清单”。

共通待确认项集中列一次，局部条件放在对应决定/数字旁；需要引用时简短指向，不反复免责。假设不能包装成事实。资料不足以推荐服务器时，先列数据增长、保存周期、索引/备份等容量因素及缺口；不得先给一个容量再加“以实际为准”。

## 读者任务走读

仅看当前成稿，尝试回答文档真正需要回答的问题。可请独立读者检查；若使用模型模拟读者，应标明模拟而非真实受众验收。

1. 读者能否定位目的、适用范围、角色/动作/结果？有没有依赖聊天记录才能理解的话？
2. 能否看清本期交付与未含事项，流程前后是否一致？
3. 金额、容量、工期、效果等关键数字是否可追溯到依据或明确假设？结论是否超过证据？
4. 能否找出需要决定/补资料的事项及其影响？必要限制是否被润色删掉？
5. 图是否回答所声明的问题，文图、明细/总额和正文结论是否一致？

每个判断应能指出对应正文位置或缺失处；不强行生成另一份大型检查表。发现问题后修正文稿，再做相应复核。内容通过后才核格式、分页、链接、图示和算术；实际未渲染就不报告视觉通过。
