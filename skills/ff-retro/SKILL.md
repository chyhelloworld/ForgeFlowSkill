# FF Retro

用户请求复盘时才执行。目标是消除已观察到的重复代价，不是制造每轮必做的健康检查。

1. 指定本次真实事件范围。只读用户提供、当前任务或已获准访问的日志、差异与测试；记录来源、发生了什么、实际代价与未知项。没有证据便说不能确认，不虚构经历、不读取受限会话记录。
2. 查仓库已有检查命令、CI、测试、导航和规范。区分机制缺失、已有但未接线、机制失效、执行没用到和纯偶发事件。不要把“没有某个钩子”自动升级成本轮问题。
3. 形成零个或少量候选：事件→可能原因→反例/替代解释→可证伪预测→最小补丁→验证成本与撤销方式。无收益证据、已有机制足够或不在范围则删除候选，零候选是有效结论。
4. 机械问题优先现有确定性检查；判断性问题才考虑精简审查规则；导航问题先补指针。先展示候选，在当前批准计划明确覆盖改动时才实施最小补丁，否则请求相应授权。不得自动改用户批准记录、权限、全局指令、安全设置或增加持久访问。
5. 以原失败样本证明能拦截，再用正常样本证明不过度拦截；加入相关回归。运行不了记未验证，不以静态文本检查冒充行为通过。若预测不成立或代价超收益，撤销本次自有改动并记录原因，不覆盖作者后续编辑。
6. 输出保留/撤销/暂缓及证据；审查独立于实现，review 绑定补丁与证据当前版本。真正批准合并、发布仍另行遵守权限；复盘候选不自动成为现行 spec。

可选候选记录见 [模板](references/template.md)。

## FF 边界

这是按需方法，不是新增强制阶段；小任务可直接完成，不要求创建完整 OpenSpec change。已有项目的当前授权、范围和文档约定优先。不因健康检查、素材缺口或复盘扩大范围。未授权的外部发送、发布、安装、持久访问或安全设置更改必须停下交用户决定。

选择使用 CLI 记录时，稳定 artifact ID、显式文件路径与依赖关系应在项目 schema/FF policy 中配置；文件存在不等于通过，生成者不得自签独立 review。审核绑定当前内容与依赖指纹；上游变化后重新判定 stale。研究、素材、文章和复盘不是产品行为规格，不放入 change 的 specs/ 增量目录，不以归档冒充用户验收或发布授权。
