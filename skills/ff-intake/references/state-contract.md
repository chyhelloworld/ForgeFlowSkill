# 轻量状态与证据契约

只复用项目已有权威载体；非规格产物复用既有位置；启用 OpenSpec FF 时，现行规格固定为 openspec/specs，策略使用稳定 ID 显式映射路径，不建立第二套数据库或常驻调度器。每份必要产物可为一段内联文字。引用原话/确认来源与版本，事实、假设、用户选择分别列明。

- Spec：已确认行为、范围/非目标、约束、可观察验收；不得将逆向代码行为自动视作承诺。
- Plan：映射 Spec 的纵向切片、边界、真实依赖、验收与当前状态；ready 只是技术可开始，不授予实施权限。
- Evidence：对应 commit/快照、环境、实际操作/原始输出与覆盖范围。状态 PASS、FAIL、NOT_RUN、BLOCKED、有理由的 N/A；指标缺数据用 NOT_MEASURED。
- Review：plan、goal-mainflow、code 各有独立结论，来源为真正独立上下文；无独立上下文标独立性未满足。
- Acceptance：用户对明确版本与范围的反馈。测试通过、技术交付、技能模拟评估与真实用户接受分别记录。

恢复时查目标/权限、工作区含未跟踪文件、环境、旧命令可观察状态及部分产物；不可查询标 unknown，不凭时间判断、不杀他人进程、不重复可能写入的未知操作。保护他人修改。

变化链：最新明确采纳来源 → 受影响目标/生产者/消费者/切片 → 失效的规格、任务、测试、审核和用户接受 → 最小修订与复验 → 可保持的无关结果。讨论可能性不等于采纳。Intake 只给对账结果；Spec、Plan、Implement 更新各自已有获准载体，Review 独立复核，Deliver 交接有效证据。新版本不能自动继承旧版本用户接受；无关证据可保留但说明适用范围。

## 老项目接手：现状与目标分开，可选只读视图

先按已有源码、运行入口、测试及历史决策核对一条相关业务主路径，给出“已观察的现状 / 原确认目标或当前候选 / 差异与未知 / 下一步”的短对账。已有文档可能陈旧，须标来源版本和未验证处；代码当前这样做，不等于用户希望这样做。没有 intent index、没有图、缺目标文档，都不阻塞接手调查，也不要求先补全索引或重新建架构档案。

用户选择可视化接手摘要时，可用已有文档显式生成离线只读视图，例如在目标项目工作区使用已安装的生成器：

```bash
node .forgeflow/dsh-plugin/generate-board.mjs --takeover --architecture-doc docs/current.md --target-doc docs/target.md --html --write
```

`--architecture-doc` 表示现状来源，`--target-doc` 表示目标/候选来源，两类分列；任一参数可省略并显示未知，无 intent index 也能运行。文档标题和引用只是线索，不证明内容正确或目标已获确认。结构化图仍须显式选择且绑定意图索引，不从零散文档自动猜图。`--html --write` 只写派生 HTML，不更新权威任务、规格、审批或验收；未选择视图时继续普通文字对账，不因缺生成器而中断接手。

发现偏差后按已有职责继续：目标/范围未明确交 Grill 或 Spec；目标清楚但剩余切片失配交 Plan；方向性技术未知才建议有界 Prove；已有授权且前置满足的实施交 Implement；独立 Review 复核原目标、主流程、计划和代码证据。只推进实际受影响部分，保留有效证据。Intake 不通过补图来批准目标、不自动重构，也不因缺索引绕过已有 policy 或关键风险审查。
