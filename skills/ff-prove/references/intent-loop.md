# 需求驱动闭环（intent-loop-v1）

目的：让用户判断“理解是否符合、现在差在哪、下一步为何”。用于持续项目、新需求、旧项目接手或实质转向；明确小改可一句需求加验收。复用现行规格、design、唯一计划和证据，不强制新文档或新阶段。同次任务已读且内容/目标/依赖未变时复用定位，不重复加载。

## 提炼与来源

从本次可访问的项目讨论、普通工作对话及 grill-me 持续提炼：目的、总需求、约束、取舍、未知。短摘要为主要展示，原话/消息/文档只作按需追溯指针。没有历史访问能力时说明实际覆盖范围和缺口，基于可见信息推进，不宣称自动读取全部宿主历史。

每项区分用户已确认、观察事实、AI假设/未知；确认带实际来源，代码现状不自动变成正确需求。目的不知道就保留未知，不能用推测取消用户明确要求。用户只需判断摘要是否符合；已有明确答复直接沿用，不让用户逐字段重新批准。仅实质影响目标、成本或关键决策的歧义才问。更新发生在有新事实/确认时，不每条消息重写。

保存沿现有授权与 Grill Mode 0/1/2：Mode 0 只在对话；已授权更新工程规格/任务时可在该载体维护精炼需求，不另问记录许可；未授权不新建讨论日志。默认本地最小摘要，聊天日志不上传。

## 需求 → 模块 → 任务 → 验收

先形成总需求，再导出子需求、用户场景及验收，最后映射功能模块和纵向任务。用已有稳定 ID；没有才取 R-/M-/T-/A- 等局部唯一 ID，改名不改 ID，语义替代保留旧→新。需求可关联多个模块、模块可支持多个需求；模块不等于页面、目录或服务。

在现有规格/设计中，每个模块只补本轮相关的职责、边界/非职责、协作（输入/输出、依赖、共享状态所有者）、验收条件引用及未知。任务引用需求/模块/验收 ID，不复制正文。原有 decision-index 指向决定、Goal 指向同一目标、Health/Resume 指向原证据；不建立第二套计划或接受状态。

要供工具读取时，在已有 design 中放一个 `intent-links-v1` JSON 块，或使用一个已授权旁置索引：`requirements[{id,ref,parent_ids}]`、`modules[{id,ref,requirement_ids}]`、`tasks[{id,ref,requirement_ids,module_ids,acceptance_ids,progress_ref}]`、`acceptance[{id,ref,requirement_ids,module_ids,evidence_refs,result_ref}]`；另有 `baseline_ref`、`source_revision`。ref 是权威文档稳定锚点/可定位 ID，未知用 null/空列表并注明缺口，不能填伪造定位。不存正文或第二份 status；状态读取 progress_ref/result_ref 的原记录，报告带观察版本/时间。这个格式只是可读关联，不是 CLI 新协议，不保证自动解析任意 Markdown。

任务 done、模块局部通过、需求验收和用户接受分别判断。跨模块场景有独立 A-ID、完整路径及结果证据，不能由模块通过率求和。总需求只有适用子需求与跨模块场景在当前版本证据上满足才可说已验收；未知/过期/缺失仍列差距，取消不是成功。

## 探索与决定转向

“如果/能否/考虑”先作探索，不创建实施任务或替换基线。形成实质转向时给短影响说明：旧/新目标差异、可复用部分、返工/迁移/维护风险、较小可选方案与主要未知。无证据不编天数/token/百分比；沉没成本不成为阻止合理变化的理由。

用户已明确决定并授权的范围直接推进，不重复确认。只有仍未决定且实质影响目标或成本的选择才请求决定。采纳后保留来源和被替代关系，局部更新需求、模块协作、任务、验收及受影响的用户接受；未受影响且仍有效的工作继续复用。

机器失效复用原 policy 的 artifact/paths/requires/inputs/指纹绑定；关联索引本身不会自动传播 stale。未登记的语义依赖必须报告并人工标待复验/阻塞依赖通过，按授权补到原被跟踪规格或依赖；不能只刷新哈希改签旧证据。独立综合审查与局部复核继续使用0.9.5节奏。

## 旧项目与缺失意图

先观察与本次任务相关的实际入口、行为和测试，再列已确认意图 / 观察事实 / 推断未知。缺历史不全仓考古。提供一次可选的针对未知的 grill-me：围绕会改变当前方案的用户目标/取舍；接受、跳过或“不知道”都合法，未知留存并注明重开条件。跳过不等于确认推断。

只有未知阻塞当前关键决定时才追问最小选择；可独立推进的授权工作继续。技术未知先小实验，不让用户答框架、数据库等技术考题。Handoff 留来源覆盖、未知及当前影响；Intake 只读核实，不自动写基线。

## UX、架构与验证

同一需求导出用户场景的触发、完整路径、关键失败/恢复和可观察结果；Design 处理可见状态/交互，Spec 处理模块协作、数据与失败语义，Prove 只验证影响方案的未知。UX 与架构相互校验，不能各自通过却无法完成同一任务。非UI场景不强造页面。

选择最简单够用架构；扩展分三档：已确认（落实必要能力）、有依据可能（记依据/触发条件，仅留低成本边界）、纯假设（暂缓，不搭框架）。必要安全、授权与数据完整性不省。先让一个完整纵向切片走通真实入口与跨模块验收，再扩展；测试不推迟到后续版本。基本流程本轮提供，强化 UX 原型/质量场景/有依据扩展演练留后续。

## 轻量收口

任务/切片完成、失败或中断时，最后承担收尾的职责在同一记录附一次使用评价；已有评价直接复用/更新。单独完成 Grill/Spec 等任务也适用，不必调用 Deliver/Retro，不每条消息评价，不要求用户回答满意度。

最短规则：需求理解、设计、交付、变化适应、成本各用“符合/问题/未知/不适用（理由）+证据指针+客观测量/用户反馈/AI推断”说明，可合成一段。无反馈不算满意，缺token/时间记缺失，不造综合分。问题用稳定ID关联版本宿主、任务目的、期望/实际、阶段影响、复现证据和归因或未知；默认在已有本地授权载体，Mode 0仅对话。任务没有发生的维度可不适用，不能为了填表制造设计或转向。

用户随时可报问题。复用已有问题记录归并同类问题，按需最小改进→失败/正常回归→真实任务复验，未复验保持待复验；不把每条问题自动变成永久门禁。有使用反馈引用的职责可按需展开格式，其余直接使用本节。脚本检查、模型合成对话、真实宿主加载和真实用户反馈分开，不把模板文字或自评当行为保证。
