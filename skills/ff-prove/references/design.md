# 按问题选择验证深度

## 实际交互未知

围绕同一个真实用户任务验证会改变方向的操作假设；如需比较结构，先说明要观察什么。纯视觉候选及审美选择交 ff-design 或既有设计流程，不能靠模拟用户结论代签。使用项目支持的简单运行方式，实际打开并操作关键状态，记录环境和视口。浏览器受阻就披露尚未观察；生成 HTML 不是用户看过。

新增区域后检查**累积完整路径**：用户从进入到目标内容/动作之间，已有与新增模块一起带来什么阅读、点击、等待负担。移动与桌面取舍不同就分别看；按实际风险覆盖打断、取消、返回、重复动作等相关状态。不要由“控件存在”推导“整体好用”，也不要凭个人审美发明像素门槛；把真实画面与已确认偏好交用户决定主观取舍。

## 逻辑或技术未知

选择最小可运行场景回答那个问题，暴露相关输入、状态与结果。验证真实路径与替身路径分开；替身/局部组件通过不能证明真实外部集成。仅在它有明确业务保护价值时选择能反驳关键假设的输入或失败情形，不穷举异常、不规定固定数量；纯视觉/资料任务不套技术负例。若注入故障，先保存与干净基线的实际差异，再判断是否触发目标症状；环境启动失败不冒充业务负例成功。

## 架构未知

先读当前调用者、变化热点、项目词表和相关决定。以行为和维护成本定位问题：同输入跨调用者有不一致吗？测试只测 helper，却绕过真正完整接口吗？

- 删除该封装后，复杂度消失，还是重新散落到真实调用者？这是判断依据，不是自动删除指令。
- 优先把行为放到可通过公开接口验证的最小合理位置；保留项目领域语言，不强制改名为某个方法论术语。
- 当前到底有什么变化需要 adapter/通用层？若只有假想未来需求，先比较简单做法；已有安全隔离、外部协议等实际职责不能仅因调用者少就删除。
- 方案应减少当下复杂度，不只新增一层。没有实际源码和调用证据不下确定重构结论。

## 记录结论

复用已有任务的一小段即可：问题和当前目标来源；范围/上限；实际操作与版本；观察到什么；未验证什么；继续/调整/停止建议及下一切片。技术可行、体验观察、用户选择分别写。需要持久记录先看原任务授权，不另建事实库或状态机。
