# FF Writing Fragments

这是素材探索，不是大纲设计。用户请求收集素材时可单独使用；不要求先 research，也不强制随后成文。

1. 从用户第一段话开始提取值得保留的原句、观察、片段、类比或问题。未知保存位置问一次；已知位置直接沿用。首写仅一个工作标题 H1，正文按自然片段排列，以横线分隔，不加目录、标签、章节大纲或固定阶段。
2. 一次问少量有助于挖掘真实细节的问题，随用户节奏停下；不得“采访到底”压过停止指令。可帮助打磨概念或命名，但模型建议应与作者实际经历区分，不能编造用户经历、数据、指标、引文或主张。
3. 每次写入前重新完整读取目标文件，保留作者删改和重排，默认只追加；仅用户明确要求时修改指定碎片。来源材料只读，不把转录原件改写成自己版本。并发变化无法安全合并则先停下核对。
4. 不擅自把碎片整理为论证顺序。缺来源的引用标待核对；缺经历问用户或删去，不补写故事。作者说停便停止，交付素材路径和未解缺口。
5. 用户明确要成文时，按写作偏好选择 shape 或 beats 之一；它们是替代路线，不是 fragments 的必经后续阶段，也不是互相前置。

素材文件格式见 [模板](references/template.md)。

## FF 边界

这是按需方法，不是新增强制阶段；小任务可直接完成，不要求创建完整 OpenSpec change。已有项目的当前授权、范围和文档约定优先。不因健康检查、素材缺口或复盘扩大范围。未授权的外部发送、发布、安装、持久访问或安全设置更改必须停下交用户决定。

选择使用 CLI 记录时，稳定 artifact ID、显式文件路径与依赖关系应在项目 schema/FF policy 中配置；文件存在不等于通过，生成者不得自签独立 review。审核绑定当前内容与依赖指纹；上游变化后重新判定 stale。研究、素材、文章和复盘不是产品行为规格，不放入 change 的 specs/ 增量目录，不以归档冒充用户验收或发布授权。

## 任务级收尾（独立使用也适用）

整个任务/切片完成、失败或中断时，按[使用反馈](references/use-feedback.md)复用已有事实附一次五维定性评价及问题指针；不是每条消息、每个写作块或每次测试循环都评价。已有记录复用，不强行调用其他技能，不自动保存或上传讨论日志。
