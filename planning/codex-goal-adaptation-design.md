# Codex `/goal` 与 ForgeFlow 的最小适配设计

状态：**研究设计，尚未实施、未作 Goal 模式端到端验收**。日期：2026-10-18 UTC。

基线：FF main `387a58943d76c4a0f4ab96a4db71b6167732502c`，版本 0.9.1、17 项技能。本文在独立文档分支保存，不改变已安装技能、CLI、门禁或 Codex 开关。用户授权是“看看如何适配 `/goal`，不适配就设计如何支持”，不是实现执行机制、合并或发布的授权。

## 1. 结论与支持层次

**宿主已有 `/goal`，FF 可以直接与它组合，但尚没有专门的目标绑定契约或自动同步集成。** 建议先做技能与使用契约的薄适配，继续复用现有规格、唯一计划、执行回执和审查；暂不增加调度器、数据库、后台服务或第 18 个技能。

| 层次 | 当前事实 | 可声明的范围 |
| --- | --- | --- |
| 已支持 | PATH 中 Codex CLI 为 `0.162.1`；桌面包为 `26.1013.3656.0`，实际运行后端为 `0.163.0-alpha.10.2`；两者 `features list` 均返回 `goals stable true` | 功能存在且当前启用，无需本轮打开实验项 |
| 已支持 | 两个本机后端生成的协议均有 `thread/goal/get`、`set`、`clear`，含 `objective`、`status`、`tokenBudget` 等字段；程序含 `/goal` 命令字符串 | 只读核实了接口形状与命令存在，未调用修改接口 |
| 可直接组合 | 无项目级 FF 技能的新 Git 项目实测发现 17 个 `scope=user` 技能；共享 `ff-spec` 与 FF 专用 CodeGraph 入口在目标项目工作 | 工具与技能可以被同一聊天选择；不等于已验证它们在 Goal 模式中完成工作 |
| 需适配 | FF 当前没有 `/goal` 专属映射、原生状态与 FF 完成条件对账、原生目标变化的恢复说明 | 本文第 3—9 节是拟议契约，不是现有能力 |
| 已验证的组合前置 | 当前桌面后端的原生只读全局 `$ff-intake` 调用成功读取技能与新项目 README，工具 completed/exit `0`；项目没有本地 FF 技能 | 已验证最小无副作用调用，不代表完整 Intake 或 Goal 模式工作流通过 |
| 仍受阻/无法验证 | PATH CLI 0.162.1 同类读取失败：`helper_unknown_error: setup refresh had errors`，工具 exit `-1`，尽管 CLI exit `0` | 执行路径对照不同，因果未确定；Goal 模式完整流程、暂停/恢复/预算强制行为未测 |

桌面 composer 菜单未直接操作；不能把后端证据写成逐按钮验收。独立 CLI 与桌面后端也不能混称为同一版本。本轮没有设置真实目标、调整预算、改变登录/凭据/安全配置或升级 Codex。

官方资料将目标限定在各自聊天；它不是账户级、跨全部项目的统一目标。[Goal mode](https://learn.chatgpt.com/docs/long-running-work)；桌面通过目标进度条管理目标，交互 CLI 另有 `/goal edit|pause|resume|clear` 形式，不能假定桌面也接受所有 CLI 参数。[桌面命令](https://learn.chatgpt.com/docs/reference/slash-commands)；[CLI 命令](https://learn.chatgpt.com/docs/developer-commands?surface=cli)。

## 2. 为什么现有 Goal Anchor 不能直接等同于 `/goal`

[Goal Anchor](../skills/ff-grill/references/clarify.md)表达为什么做、为谁做、成功、非目标、约束和确认来源。[Spec](../skills/ff-spec/SKILL.md)定义可观察行为；[Plan](../skills/ff-plan/references/slicing.md)把已确认要求拆成可验收切片。它们已经覆盖许多目标管理语义。

原生 `/goal` 则是宿主保存的聊天目标及运行状态。它的短文本不承载完整 FF 规格或审核回执；宿主判断完成，也不能代替 FF 的业务证据和真实用户接受。反过来，FF 的 `valid`、`RECORDED`、任务勾选也不能证明宿主目标状态已经更新。

因此保留一份项目权威要求：`openspec/specs/` 为现行规格，活动变更在 `openspec/changes/`，计划沿用项目已有载体。原生目标只放短结果、边界、完成判据与这些来源的指针，不复制完整规格、不把目标文本变成第二套现行规范。

## 3. 目标、计划与完成条件映射

以下是建议的映射表，放在已有计划/获准交接位置或当前对话即可；不强制新建 `goal.json`。

| FF 项 | 原生目标中的表达 | 权威、变化与验证 |
| --- | --- | --- |
| Goal Anchor | 目标结果、非目标、关键约束及定位 | 只引用最新用户确认的目标与来源；模型提炼的部分仍待确认 |
| Spec | 必须实现的主流程与可观察完成条件，引用规格条款 | 现行规格与活动变更保留各自角色；未批准候选不升格 |
| Plan / Tickets | 指向唯一计划，当前可做切片与稳定 ticket/action ID | 工作票是计划的切片视图，不另建执行状态库 |
| 验收 | 真实主流程证据、适用审核及需要的人类接受 | 明确行为、技术检查、用户接受三者；测试通过不等于业务价值已证实 |
| 恢复 | 项目身份、已确认目标修订号、依赖与回执指针 | 沿用 checkpoint 的 `goalRevision`、依赖哈希和 action ID；不从旧检查点反推最新目标 |

原生观测只需：宿主/版本、当前聊天定位、目标文本及读取时间、可见状态；预算可见时一并记其来源。聊天 ID 只在确有恢复需要且获准的位置使用，不导出账户标识、凭据或私人会话。原生目标文本变化应与用户最新意图核对；`updatedAt` 也可能因状态或预算变化更新，不能直接当 FF 的语义修订号。

**本轮完成定义**应由结果、必要证据、适用审查、未完成项及真实接受共同组成。例如，未来隔离样例可要求“数量 2、单价 12 的发票保存后重开仍显示 24”；这是拟议测试产品，当前 CodeGraph 中存在同名算价函数不证明保存行为已实现。

## 4. 一个工作单元与阶段审查

沿用可交付纵向切片，不把每个函数、文件或技能都变成工作票。每片只补必要信息：ticket ID、对应规格、输入版本/依赖、稳定 action ID、主要验收入口、授权依据、范围/预算与停止边界。必要技术前置可以单独验证，但不能计为用户功能完成。

运行单元的建议顺序为：

1. Intake 对账当前目标、项目、修改状态、授权和旧执行结果；有明确有效计划时直接复用，不重走全套澄清。
2. 选一个前置齐全且获准的切片；先确认主要验收路径可运行，宿主读取已失败时不大规模扩展实施。
3. 执行并留真实结果：argv/cwd、exit、产物/测试版本、必要哈希和失败；只保存任务所需证据。
4. 对应阶段做审查：计划看目标映射/边界/依赖与 MECE；目标与主流程看实际行为；代码看规范及同版本计量。小改可同一独立读者覆盖适用项，无需强制三人。
5. 对账下一片与剩余预算；工作区、规格或依赖变化只使受影响结果失效。技术完成、待人类验收、受阻分别报告。

复用 [Health](../skills/ff-review/references/health.md) 的 `goal-mainflow`、`plan`、`code`。必要独立性不可用就披露；代码计量缺复杂度或同版本覆盖率时为 `NOT_MEASURED`，不能写 0 或宣称所有函数 CRAP 通过。仍保留硬上限 50、目标约 10；纯文档审查可按现有协议写有理由的 N/A。

这些是技能执行契约。没有外部控制器时，提示词不能强制拦住另一写入者，也不能保证所有模型行为都遵守它。

## 5. 中途新增需求与原生目标编辑

| 用户输入 | 处理建议 |
| --- | --- |
| “能不能支持 CSV？”或比较方案 | 回答/澄清，保持候选；不追加工作票、不修改规格或 native goal |
| 明确“把 CSV 加入本轮”，已有实施授权覆盖 | 视为明确范围指令，保存真实来源，更新受影响规格、任务、验收与依赖；不机械重复请求同一授权 |
| 新目标、显著预算/约束变化或范围尚不清楚 | 先做影响分析，只问仍需用户决定的取舍；依赖它的工作暂停，无关获准部分可继续 |
| 只要求设计 | 只交设计与验证计划；工作区快照应证明没有实现代码变更 |
| 用户直接编辑 `/goal` 文本 | 核对与既有目标/规格的差异；编辑是用户意图来源，但不能凭一个模糊目标替所有候选方案或高影响动作取得授权 |

明确采纳且语义目标/范围改变时，使用新的目标修订号（如 R1→R2），让当前锚点、规格、计划和交接引用保持一致；单纯暂停/恢复、统计或状态变化不升级语义修订号。继续使用唯一计划，保留历史/失效说明。需要修改宿主目标时，首版由用户使用原生 UI/命令完成；没有可调用且获准的状态接口时，不用“已同步”“已暂停”等文字冒充实际操作。

## 6. 预算、停止与原生状态

本机生成的 `ThreadGoal` 有 `tokenBudget`、`tokensUsed`、`timeUsedSeconds`；状态为 `active`、`paused`、`blocked`、`usageLimited`、`budgetLimited`、`complete`。`ThreadGoalSetParams` 有可选 `tokenBudget`，没有壁钟截止时间字段。本轮只核实协议形状，没有测预算强制停止，也不发明 `/goal --budget` 参数。

预算沿用用户给定上限及实际宿主可见值；不可见写 unknown，不当无限或 0。FF 计划中的时间/动作数上限属于指令约束，首版没有系统级硬停止保证。每片开始及长操作前核对预算；无法证明仍在明确硬预算内，就停止依赖该预算的新操作并说明缺口。

| 情况 | 执行与报告 | 原生状态边界 |
| --- | --- | --- |
| 前置齐全、预算与授权覆盖 | 做下一获准片 | 只按实际观测报告 active |
| 需要用户选择、证据或权限 | 停止受影响动作，给最小问题/缺口 | 可建议 pause；不能宣称 UI 状态已变 |
| 用户暂停/停止 | 不再启动新动作，盘点自己未完操作和部分产物 | paused 不证明所有已启动子进程已被终止 |
| 配额/预算不足 | 留短检查点并等待有效续做条件 | 不切账号、模型或权限来绕过限制；只报告实际受限状态 |
| 宿主工具故障 | 保留失败，停止依赖该工具的执行 | CLI exit 0 不能覆盖工具 failed/-1 |
| 技术达成但待人类接受 | 交付证据与验收入口，不宣称 FF 最终完成 | native complete 与 FF 接受分开；不能伪造或静默改写状态 |

`/goal` 继承聊天现有沙箱和审批边界；不扩大文件、网络、发布、付费或凭据访问。既有明确授权继续有效，不逐片重复审批；越界动作仍走实际门禁。目标文字或 `origin=user` 字段不是新的安全边界。

## 7. 中断恢复与避免重复副作用

复用 [continuity](../skills/ff-implement/references/continuity.md) 与 [resume 协议](../skills/ff-handoff/references/resume.md)。首版不改 checkpoint JSON 结构：

1. 新上下文先核对本聊天目标、用户最新确认、项目身份、HEAD/dirty/untracked、既有唯一计划与权限。原生目标不可读时明确 unknown，通过当前用户信息核对，不能照抄旧检查点。
2. 根据本次核实的最新目标向 resume 传 `--current-goal R2`，并核对目标/规格/计划/源码等实际依赖。R2 不是从旧 checkpoint 取来的“答案”。
3. 在同一有效目标修订及全局检查通过时，版本、依赖和完成回执都有效的动作才得到 `SKIP_COMPLETED`；待执行为 `VERIFY_CURRENT_AUTHORITY`；running/unknown、陈旧或缺回执为 `INSPECT`。**现有 resume 对全局目标修订不匹配会先把全部动作标为 INSPECT；它不自动计算“只有哪些动作受影响”。**
4. 对有副作用的 unknown，先用获准的只读状态、稳定操作 ID、实际产物/目标系统回执对账。可能已生效而未记账的操作不得盲重跑。外部系统无法核验时停在 INSPECT。
5. R1→R2 后由调用者重新做影响与适用性对账，只实际复做受影响工作；保留未受影响的原始证据，但不能改签旧回执、伪报新执行或直接把 R1 done 改成 R2 done 来通过检查器。若需要当前修订下可机器核对的状态，须有真实只读适用性复核的新记录，明确它是复核而不是重跑原操作，原执行日志保持原字节；工具不会自动生成或证明这份复核。条件不具备时保持 INSPECT。
6. 仅在获准工程/交接载体更新短检查点。Mode 0 不额外保存讨论日志；设置原生目标也不等于允许复制整个聊天。不得读取私有 sessions 或搬运凭据来恢复。

resume 是只读核对器，不是执行器、权限服务或锁；不保证进程存活、事务性、exactly-once、自动唤醒或抵抗恶意篡改。原生恢复同一聊天也不能代替这次对账。

## 9. 用户使用流程（拟议，未执行）

1. 在目标项目打开 Codex，确认实际技能路径/版本与 CLI 可用；旧项目同名技能可能同时显示，显式选择本轮目标版本。项目的需求、计划和回执仍留本项目。
2. 目标不清时用 `/plan` 配合 FF 澄清；已有明确有效计划则直接引用，不重新问一遍。
3. 用户设置一个具体 `/goal`，例如：

   ```text
   /goal 按本项目已确认的发票规格完成剩余切片；只做本地开发与主流程验证。
   保留已有修改，不合并或发布；完成条件是规格指定的实际行为、适用独立审核及证据齐全。
   尚缺约定用户验收时明确待验收，不宣称最终完成。引用现有唯一计划，不另建任务库。
   ```

4. 再显式请求 `$ff-intake` 核对当前目标/项目/权限与既有回执；不要假设仅把技能名写进目标字符串就一定加载了技能。
5. 在同一聊天按获准切片推进；用户追加要求时按第 5 节归类。桌面用进度条暂停/恢复/编辑/清除；CLI 使用其对应命令。预计断连时先暂停并留下获准检查点。
6. 恢复时重新 Intake + 必要 resume；目标达成后给真实证据、未测与接受状态。不要凭目标条状态修改项目事实。

## 10. 具体验收用例与验证办法

以下是未来验收计划，**均为 NOT_RUN**，没有因为本轮安装/图谱测试通过而改成通过。只覆盖主要工作旅程及高价值失败场景，不穷举字段/函数。

| ID | 场景/输入 | 必须观察到的结果与证据 |
| --- | --- | --- |
